## Goal

```
재고 ──재고 부족──> 결제: 환불       ✚ 새로 생김
결제 ──환불됨──> 알림: 메일 보냄     ⚪ 원래 있던 흐름
알림 ──> 메일 서버 ──> ...           ⚪ 원래 있던 흐름
```

## Decisions Made

**후보 1: 경로 그림은 진입점에서 시작한다**

- **Q1 적용 범위:** 경로 그림에만 적용한다. 구조 그림에는 진입점이 없다. Whiteboard도 `call_stack_diff` 한 종류에만 둔다.
- **용어 "경로 그림".** "흐름 그림", "유저 플로우", "요청 경로 그림"은 버렸다(뜻이 겹침). CONTEXT.md에 있다.
- **경로 그림에 들어가는 상황 6개:** API behavior, Authentication and authorization, Retry and branching, Saga, Queue and batch pipeline, Performance bottleneck. 제외: Data flow and derived data, Incident response flow, 구조 그림, 시간표 그림.

**Q2 바뀌는 것을 어떻게 보여 주나 → 색 정책 전체**

- **한 그림**에 지금 코드 + 바뀔 것을 그린다. 변경이 크면 지금/바뀐 뒤 두 그림을 나란히(PRD "변경안 표기"에 이미 있는 규칙). 두 그림만 쓰면 없어지는 것이 "그냥 안 보여서" 사용자가 눈으로 비교해야 하므로 기본으로 하지 않는다.
- **Whiteboard 호출 트리는 가져오지 않는다.** 함수 단위다. 구현 전에는 새 절반이 에이전트의 구현 계획이고, 함수 단위는 사용자가 맡기는 영역이다. PRD도 "줌 레벨은 경계 타입에서 끝난다"고 한다. "코드 어디가 바뀌어?"에는 텍스트(파일:줄)로 답한다.
- **변경 상태 색 3개를 고정한다:** 초록 = 새로 생김, 빨강 = 없어짐, 노랑 = 수정됨. 모든 그림에서 같다. 이유: 오해를 잡는 데 직접 쓰이는 색이라 매번 범례를 읽지 않아도 되어야 한다.
- **3색은 사용자가 요청해도 다른 뜻으로 쓰지 않는다.** 이유: 사용자도 캔버스에 그린다. 사용자가 그린 초록 선은 "추가하자"로 읽어야 한다. 요청이 오면 에이전트는 이유를 한 줄 말하고 다른 색을 제안한다(예: 초록 대신 청록). Whiteboard는 3색을 다른 상자에 다시 쓰지만, 우리는 더 엄격하다.
- **종류 색을 없앤다:** 서비스 = 보라, 큐 = 주황, DB = 청록, 파랑 = 주 경로, 빨강 = 에러, 초록 = 성공. 이유: 박스 이름이 이미 말하는 것을 반복하고, 사용자가 원하는 "모듈별 색"을 막는다.
- **기본 색:** 흰 박스 + 검정 선. 사용자가 명시적으로 요청하면 에이전트가 색을 알아서 고른다. 3색은 빼고 고른다.
- **실패 경로:** 검정 + 상태 코드 글자(예: `409 Conflict`). Whiteboard 그림에도 에러 색이 없다.
- **화살표:** 초록·빨강만 쓴다. 노랑 화살표는 쓰지 않는다. 화살표가 바뀌면(이름만 바뀌어도) 옛 것은 빨강으로 남기고 새 것은 초록으로 더한다. 이유: 노랑 하나로 그리면 옛 것이 안 보여서 무엇이 없어지는지 확인할 수 없다. Whiteboard는 이름만 바뀌면 "수정됨" 하나로 세지만 우리는 규칙 하나로 단순하게 간다.
- **노랑은 박스에만 쓴다.** 뜻: 박스는 그대로 있고 안에서 하는 일이 바뀐다(예: 결제 박스에 "실패하면 3번 다시 시도"가 생김, 화살표는 그대로).
- **바뀐 박스: 연한 색 채우기 + 같은 색 테두리.** 테두리만 칠하는 방법(채우기는 모듈 색)과 캔버스에서 비교했다. 사용자가 채우기를 골랐다. 이유: 한눈에 보여서 놓치지 않는다. 모듈은 경계 박스가 보여 준다. Whiteboard 흐름 그림과 같은 방식이다.
- **색 + 고정 영어 글자:** `added` / `removed` / `modified`. 이유: 적록색약도 뜻을 읽을 수 있다. 에이전트가 글자를 쓰면 무엇을 없앤다고 이해했는지 한 번 더 분명해진다. Excalidraw 글자에는 취소선이 없다. 지금 규격의 `[sync]`, `inferred`와 같은 방식이다.
- 정확한 hex는 정하지 않았다. 캔버스 비교 때 쓴 값은 Excalidraw 팔레트다: 초록 `#2f9e44`/`#b2f2bb`, 빨강 `#e03131`/`#ffc9c9`, 노랑 `#f08c00`/`#ffec99`. 노랑 선 색 `#f08c00`은 주황처럼 보인다. 채우기로 쓰면 노랑으로 보인다.

**Q3 어디까지 그리나**

- **진입점부터 안 바뀐 단계도 넣는다.** 사용자가 (a) 예시(안 바뀐 단계 포함)를 받아들였다. Whiteboard 규칙과 같다.
- **200 응답에서 끝내지 않는다. 바뀐 부분이 만든 뒤쪽 흐름까지 그린다.** 예: 재고 차감을 이벤트로 바꾸면 응답이 먼저 나가고 차감은 뒤에 일어난다. 뒤쪽이 빠지면 "응답 뒤에 차감이 실패하면?"을 에이전트가 어떻게 이해했는지 확인할 수 없다. Whiteboard에는 이 규칙이 없다. Whiteboard는 구현 뒤에 그리고 우리는 구현 전에 그리기 때문에 우리에게 필요하다.

## What Worked

- **캔버스에 직접 그려서 보여 주기.** 사용자가 "테두리가 잘 보일까?"라고 망설일 때 두 방법을 archdraw 캔버스에 그려 스크린샷을 보여 줬다. 바로 결정이 났다. 헷갈리는 시각 선택은 말 대신 그린다.
- **아주 짧게, 한 번에 하나.** "규칙 3줄 + 이렇게 할까요?" 형태가 가장 잘 통했다.
- **구체 예시 하나로 문제 설명.** "직접 요청을 없앤다"와 "남기고 이벤트를 더한다"가 **같은 그림**이 된다는 예시로 문제가 전달됐다.

## What Didn't Work

- ⚠️ **답이 길고 어려웠다.** 사용자가 여러 번 "무슨 말이야", "장황하게 말하지 마"라고 했다. 표, 선택지 3개, 이유 여러 줄을 한 번에 주면 안 된다. 규칙: 짧은 문장, 한 문장에 한 뜻, 한 번에 질문 하나.
- ⚠️ **설명 없는 말을 썼다.** "선이 바뀌면", "방법 1", "노랑"을 풀지 않아서 사용자가 이해하지 못했다. 처음 쓰는 말은 예시와 같이 쓴다. "선"은 "박스 사이의 화살표"라고 먼저 말한다.
- ⚠️ **Whiteboard를 확인하지 않고 질문했다.** Q2-2~Q2-6을 Whiteboard 분석 없이 물었고 사용자가 지적했다. 질문마다 설명 순서를 지킨다: **우리는 어떻게 하나 → Whiteboard는 어떻게 하나(코드로 확인) → 예시 → 추천.** 확인 못 한 것은 "확인 안 함"이라고 말한다.
- ⚠️ **"사용자가 요청하면 따른다"류의 느슨한 규칙을 제안하지 않는다.** 사용자는 3색에 대해 "요청해도 안 쓴다"로 분명히 정했다.
- ⚠️ **결정을 다시 묻지 않는다.** 채우기 vs 테두리에서 사용자가 망설였을 때 추천 하나를 분명히 말해야 했다("채우기로 합시다").
