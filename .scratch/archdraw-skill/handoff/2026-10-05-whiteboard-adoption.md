## What Worked

- **문제를 파일의 실제 줄과 "누가 무엇을 고치면 무엇이 일어나는가"의 순서로 설명했다.** "박스 크기가 세 번 적혀 있다 → 73줄만 220으로 고친다 → 검사는 통과한다 → 박스는 200으로 나온다". 사용자가 바로 이해했다.
- **추천마다 근거를 표로 붙였다:** 확인한 사실 / 추정 / 맞는 원칙 / 버린 선택과 이유. 사용자가 "너의 추천을 어떻게 믿지?"라고 물은 뒤에 시작했다. 계속 쓴다.
- **고친 뒤에 "보여 준 표와 다른 것"을 따로 보고했다.**
- **이슈 문서는 전체 경로로 부른다.** 순서 표의 열: 순서, 이슈 문서, 일, 상태.
- 계속 유효(이전 세션): 설명 → 질문 하나 → 범위 표 승인 → 구현. 첫 보고에서 사용자의 목표와 문제를 에이전트의 말로 다시 말한다. 틀린 것은 틀렸다고 말한다.

## What Didn't Work

- ⚠️ **"2번"처럼 번호만으로 부르면 통하지 않는다.** 에이전트가 "2번"을 순서 표의 2번째와 보고의 2절 두 뜻으로 썼고, 사용자는 이슈 문서 02로 읽었다. 일은 이름("그림 목록 작업")과 이슈 문서의 경로로 부른다.
- ⚠️ **긴 보고는 통하지 않는다.** "장황하게 말하지 마"를 두 번 들었다. 통한 길이: 결론 한 줄 + 표 하나(3~4줄) + 질문 하나. 선택지의 근거 표는 사용자가 물을 때만 길게 쓴다.
- ⚠️ **확인하지 않은 말을 사실처럼 말했다.** "중복은 없앨 수 없다"(파일 머리말에 반대 사실이 있었다), "지우면 덜 지킬 수 있다"(근거가 없었다), "5개 중 3개가 겹친다"(5개 모두였다). 사용자가 근거를 물어서 드러났다. 말하기 전에 파일에서 확인하고, 추정은 "추정"이라고 적는다.
- ⚠️ **싼 선택을 추천하지 않는다.** 사용자는 "정석이 무엇이냐"를 묻는다. 프로젝트의 원칙에 맞는 선택을 먼저 추천하고, 비용은 따로 적는다.
- ⚠️ **"스킬 문서가 아니다"처럼 폴더로 구분한 말은 틀렸다.** 위 Context 참조.
- **`grilling` 스킬의 "문제가 이해됩니까?" 질문을 너무 많이 했다.** 사용자는 "그래서 어떻게 하자고?"로 답했다. 문제 설명 바로 뒤에 고치는 방법과 질문을 같이 낸다.
- 계속 유효(이전 세션): 추상적인 문장 대신 예시로 말한다. 보고와 결정 요청을 섞지 않는다. 승인받은 범위만 고친다. 없는 손해를 만들어 말하지 않는다. 개수는 목록을 세고 말한다.
