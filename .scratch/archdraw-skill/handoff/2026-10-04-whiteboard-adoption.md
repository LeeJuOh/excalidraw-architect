# Whiteboard 도입: PRD의 미결은 0개다. 다음은 이슈 5개를 PRD에 맞춘다

## Goal

**최상위 원칙(사용자의 말 그대로): "당신이 무엇을 요청해도, 에이전트가 그 상황에 알맞은 그림을 정석대로 그린다."**

사용자는 설계(아키텍처, 경계, 트레이드오프)를 정하고 구현을 위임한다. 사용자는 코드를 직접 보지 않고 에이전트의 말만 본다. 말만으로는 둘의 이해가 같은지 알 수 없다. 그림은 서로의 이해를 대조하는 면이다(`.scratch/archdraw-skill/spec.md` → "Problem Statement"). 그림의 종류가 틀리거나 필요한 것이 빠지면 오해가 그림에 보이지 않는다.

Whiteboard 도입 그릴의 결정은 모두 끝났고 PRD(`spec.md`)에 반영했다. **남은 일의 순서(사용자가 승인했다): PRD → 이슈 문서 → 구현.** 새 PRD나 새 이슈를 만들지 않는다. 있는 PRD와 있는 이슈를 고친다.

## First Action

두 단계다. 사용자에게 묻기 전에 1번을 에이전트가 끝낸다.

1. **`spec.md`에서 이번 세션이 읽지 않은 3곳을 읽는다:** "Solution" 절, "Out of Scope" 절, "구현 이슈와 진행 순서"의 이슈 표. Whiteboard 결정(아래 "Decisions Made"와 `spec.md`의 스토리 41~51)과 다른 문장이 있는지 본다. 이것은 사실 확인이다. 사용자에게 "확인할까?"라고 묻지 않는다.
2. **사용자에게 결과를 한 줄로 말하고 질문 하나를 한다:** "PRD는 다 고쳤다(또는: 이 한 곳이 남았다). 이제 이슈 문서 5개를 PRD에 맞게 고칠까?" 이슈가 무엇인지 한 줄로 말한다("구현할 일을 적은 문서"). 승인을 받으면 "Next Steps" 1번의 표대로 고친다.

⚠️ 이번 세션에서 이슈 03을 고치기 시작했을 때 사용자가 수정을 거부했다. 사용자가 "이슈를 고친다"를 분명히 승인한 뒤에만 이슈 파일을 고친다.

## Context

- **결정의 원본은 `spec.md`다.** 이 핸드오프는 결정을 다시 적지 않는다. `spec.md`에 없는 것(색값, 지울 문장의 자리, 이슈마다 바꿀 내용)만 적는다.
- **PRD를 고친 방법(이전 세션):** `/mattpocock-skills:to-spec`의 틀(Problem, Solution, User Stories, Implementation Decisions, Testing Decisions, Out of Scope, Further Notes)의 절마다 고쳤다. 테스트할 자리(시임) 4개는 사용자가 승인했다(`spec.md` → "Testing Decisions"의 마지막 항목).
- **규칙을 만드는 기준(사용자의 원칙):** 모델이 잘 판단하고 결과가 그림에 보이는 선택은 규칙으로 정하지 않는다. 그림에서 빠진 것은 사용자가 볼 수 없으므로 필수요소 목록은 남긴다. `spec.md` → "규칙을 만드는 기준".
- **질문하기 전에 하나만 본다: "이것이 '요청 → 알맞은 그림'을 바꾸나?"** 바꾸지 않으면 묻지 않는다.
- **한 번에 한 질문만 한다.** `grilling` 스킬의 라운드 방식보다 사용자의 방식이 우선이다. 사실 확인은 에이전트가 한다. 질문에는 추천 하나를 붙인다.
- 사용자는 ADHD가 있다. 긴 설명을 싫어한다. 결론 한 줄 → 작은 표나 예시 하나 → 질문 하나 순서로 말한다.
- **사용자의 말로 말한다.** 사용자는 "상황", "필수요소", "시임", "의존 도달 범위", "행" 같은 우리 문서의 말을 모른다. 통한 말: "그림 목록", "줄", "칸(레인)", "꼭 있어야 하는 것의 목록", "규칙 1 / 규칙 2", "공통 룰 / 한 줄만의 내용".
- 사용자는 에이전트의 추천을 그대로 받지 않는다. 근거를 묻고, 과장한 것을 지적한다.
- 파일은 사용자가 승인한 뒤에 고친다. 커밋과 푸시는 사용자가 지시할 때만 한다.
- **세션이 끝난 순간:** 사용자가 "prd는 다고쳣고?"라고 물었다. 에이전트는 "확인한 것 / 읽지 않은 것 / 미확정 2개"를 나누어 길게 답하고 "3곳을 확인할까, 이슈로 갈까?"라고 물었다. 사용자의 말: "먼소리야 핸드오프해". 답이 길었고, 에이전트가 할 일을 질문으로 넘겼다.

## What Worked

- **캔버스를 비우고 견본 2개만 남겼다.** 사용자가 "캔버스에 필요한것만 남겨 헷갈려"라고 했다. 견본을 그리기 전에 이전 그림을 스냅샷과 파일로 저장했다.
- **충돌을 "규칙 1 / 규칙 2"로 말했다.** 색 이름과 표기 방법으로 설명한 두 번은 실패했다. "문서에 충돌하는 규칙이 2개 있다. 하나를 지워야 한다. 규칙 2를 지워도 돼?"가 통했다.
- **범위를 "공통 룰 / 한 줄만의 내용"으로 말했다.** 사용자가 "지금 이거 공통룰이야?"라고 물었을 때 그림 목록의 예시 표 하나와 범위 표 하나로 답했다.
- 이전 세션의 교훈(계속 유효): 고치기 전에 범위를 표로 보여 주고 승인받는다. 이슈를 만들기 전에 용어 사전과 ADR에 대조한다. 요청 → 그림 예시 한 줄. 틀린 것은 틀렸다고 말한다.

## What Didn't Work

- ⚠️ **결정을 묻기 전에 표기 방법부터 설명했다.** "파랑, 초록, 노랑, 굵은 테두리"의 표를 두 번 보여 줬다. 사용자의 말: "먼소리지 이해가안가 … 멀물어보는거지 의도가 머지 요지가머지". 먼저 요지 한 줄("무엇이 문제이고 무엇을 정해야 하나")을 말한다. 세부는 사용자가 물을 때 말한다.
- ⚠️ **없는 손해를 만들어 말했다.** "잃는 것 1개: 전체 중 몇 개가 닿나가 보이지 않는다"고 했다. 사용자가 지적했다: "그냥 관계없는 모듈 안그리면 된느거아냐?" 추천의 약점을 채우려고 약점을 만들지 않는다.
- ⚠️ **애매한 지시를 확인하지 않고 파일을 고치기 시작했다.** 사용자가 `/mattpocock-skills:to-spec 고치자`를 보냈다. 에이전트는 "이슈 5개를 고치자"로 읽고 `Edit` 8개를 보냈다. 사용자가 모두 거부했다: "아 잠깐 이슈문서 고치기엿어?" 명령(PRD를 쓰는 스킬)과 직전의 질문(이슈를 고칠까?)이 맞지 않으면 한 줄로 확인한다.
- ⚠️ **에이전트가 할 사실 확인을 질문으로 넘겼다.** "읽지 않은 3곳을 확인할까?"라고 물었다. 사용자의 말: "먼소리야". 읽고 나서 결과를 말한다.
- **첫 견본을 기존 그림 아래에 붙였다.** 캔버스에 예시 3벌과 글꼴 견본이 같이 보여서 사용자가 헷갈렸다. 질문용 견본은 빈 자리에 따로 보여 준다.
- 이전 세션의 교훈(계속 유효): 설명 없이 낯선 주제의 질문을 하지 않는다. 핸드오프의 할 일 목록보다 프로젝트의 문서 순서(`AGENTS.md` → "문서 위치")를 먼저 본다. 내부 번호와 내부 이름을 보여 주지 않는다. 확인하지 않은 것을 한계처럼 말하지 않는다. 경우마다 규칙이나 새 줄을 제안하지 않는다. 개수는 목록을 세고 말한다.
