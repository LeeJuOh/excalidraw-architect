## Decisions Made

### 후보 1 — 적용 범위와 그림

- 경로 그림에만 진입점 규칙을 적용한다. 구조 그림과 시간표 그림에는 적용하지 않는다. “경로 그림” 정의는 `CONTEXT.md` → “경로 그림”.
- 적용 상황 6개: API behavior, Authentication and authorization, Retry and branching, Saga, Queue and batch pipeline, Performance bottleneck. Data flow and derived data, Incident response flow는 제외한다.
- 현재 코드와 변경안을 기본적으로 한 그림에 담는다. 변경이 크면 현재/변경 후 두 그림을 나란히 둔다. 없어지는 것도 보이도록 한다.
- Whiteboard의 함수 단위 호출 트리는 가져오지 않는다. 줌은 경계 타입에서 끝난다. 코드 위치 질문에는 파일·줄을 텍스트로 답한다.

### 후보 1 — 변경 상태 색

- **초록 = 새로 생김, 빨강 = 변경안에서 없앨 것, 노랑 = 수정됨.** 모든 그림에서 같은 뜻이다. 사용자가 요청해도 다른 뜻으로 쓰지 않는다. 사용자의 같은 색 편집도 같은 뜻으로 읽는다.
- 기본은 흰 박스·검정 선이다. 서비스·큐·DB·주 경로·성공·실패의 종류 색은 없앤다. 실패는 검정과 상태 코드 글자로 나타낸다.
- 사용자가 색을 명시적으로 요청하면 에이전트가 세 변경 상태 색을 제외하고 고른다. 요청이 고정 색의 뜻과 충돌하면 이유를 한 줄 설명하고 다른 색을 제안한다.
- 바뀐 박스는 연한 채우기와 같은 계열 색 테두리를 쓴다. 색과 함께 `added` / `removed` / `modified`를 고정 영어 글자로 쓴다. 색 구분이 어려워도 뜻을 읽을 수 있어야 한다.
- **바뀐 화살표**에는 초록·빨강만 쓴다. 이름만 바뀌어도 옛 화살표는 빨강으로 남기고 새 화살표를 초록으로 더한다. 노랑은 박스가 남고 안에서 하는 일이 바뀔 때만 쓴다.
- 변경 상태 채우기를 우선하고 모듈 구분은 경계 박스로 보여 준다. 채우기와 테두리만 칠하는 방식을 캔버스에서 비교한 뒤 사용자가 채우기를 골랐다.
- 정확한 색값은 미확정이다. 이전 비교에 쓴 값을 확정된 규격이나 승인된 기본값으로 취급하지 않는다.

### 후보 1 — 경로의 범위

- 진입점부터 바뀐 단계에 닿기 전의 기존 단계도 넣는다. HTTP 응답에서 끝내지 않고 변경이 만든 이후 처리도 담는다.
- **Q3-2 합의:** 이번 변경을 판단하는 데 필요한 부분만 그리고, 나머지는 생략했다고 표시한다. 사용자는 그대로 두거나 궁금한 부분을 더 그려 달라고 요청할 수 있다.
- 결과나 실패 처리를 확인하는 데 필요한 단계는 기존 처리라도 포함한다. 첫 기존 단계를 만나면 무조건 멈추는 규칙이 아니다.
- 설명 예시: 새 환불 처리 → 기존 알림까지 보여 주고 이후 메일 발송은 `…`로 생략할 수 있다. 메일 발송이 판단에 필요하면 포함한다.
- Whiteboard `references/whiteboard/packages/review/instructions/authoring.md` → `call_stack_diff`는 진입점과 기존 단계 포함을 정하지만 종료 기준은 정하지 않는다.

## What Worked

- 짧은 문장, 한 문장에 한 뜻, 한 번에 한 질문.
- 구체 예시에서 새로 바뀌는 단계와 기존 단계를 분명하게 구분하기.
- 시각 선택은 말로 길게 설명하지 않고 실제 캔버스에서 비교하기.

## What Didn't Work

- ⚠️ “뒤쪽 처리” 같은 말을 맥락 없이 썼다. 후보와 변경 예시부터 설명한다.
- ⚠️ 출처 없는 기존 PRD 문구를 이미 합의한 기능으로 취급했다. “문서에 있음”, “외부 근거가 있음”, “사용자가 승인함”을 구분한다.
- ⚠️ 방향 확인 질문을 스펙·스킬 적용 지시로 읽었다. 이어서 핸드오프 기록까지 취소했다. 결정 기록은 계속하고, 실제 적용은 별도로 지시받는다.
- 표·여러 선택지·긴 배경을 한 번에 주면 이해가 어려웠다. 질문에 필요한 예시 하나와 추천 하나만 먼저 제시한다.
