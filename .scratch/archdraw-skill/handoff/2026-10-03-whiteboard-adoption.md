# Whiteboard 도입 그릴: "목록에 맞는 줄이 없는 요청"부터

## Goal

**최상위 원칙(사용자의 말 그대로): "당신이 무엇을 요청해도, 에이전트가 그 상황에 알맞은 그림을 정석대로 그린다."**

사용자는 설계(아키텍처, 경계, 트레이드오프)를 정하고 구현을 위임한다. 사용자는 코드를 직접 보지 않고 에이전트의 말만 본다. 말만으로는 둘의 이해가 같은지 알 수 없다. 그림은 서로의 이해를 대조하는 면이다(`.scratch/archdraw-skill/spec.md` → "Problem Statement"). 그림의 종류가 틀리거나 너무 얕으면 오해가 그림에 보이지 않는다.

이 그릴은 Whiteboard에서 가져올 후보를 한 번에 하나씩 정한다. 후보의 원본 근거는 `.scratch/archdraw-skill/research-whiteboard.md` → "3. 가져올 것" 표다. 이 문서의 후보 번호는 **그릴 순서**이고, 표의 `#`와 다르다.

## First Action

`/grill-with-docs`로 재개한다. 보고의 맨 위에 위의 최상위 원칙을 쓴다. 그다음 질문을 **하나만** 한다: **"그림 목록에 맞는 줄이 없는 요청을 어떻게 다루나."** 아래 내용을 짧게 설명한 다음에 묻는다.

- **요지:** 원칙은 "무엇을 요청해도 알맞은 그림"이다. 그런데 스킬은 요청을 21개 질문 중 하나로 읽으라고만 한다. 맞는 줄이 없을 때의 문장이 없다.
- **예시:** 사용자가 "Order 애그리거트 안을 보여줘"라고 한다. 알맞은 그림은 클래스 다이어그램이다(사용자의 말). 그림 목록에 클래스 다이어그램이 없다. 그리고 금지 문장 2개가 막는다.
- **확인한 사실:**
  - `plugin/skills/archdraw/SKILL.md` → "6. Pick the diagram from the question"의 첫 문장: "Read the user's words as one of the twenty-one questions". 맞는 줄이 없는 경우의 문장은 그 절에 없다.
  - 금지 문장 2개는 `plugin/skills/archdraw/references/zoom-levels.md`에 있다. "How zooming actually runs"의 "L5 holds boundary types only — ports and their implementations. Do not list the classes inside; that list goes stale fastest." 그리고 "DDD mapping"의 "Do not list the entities inside an aggregate."
  - "애그리거트 내부 엔티티는 안 나열"의 이유는 우리 기록에 없다(`spec.md`, `review.md`, `research-structure.md`, `docs/adr/0004-five-zoom-levels.md`를 검색했다).
  - 안쪽 그림을 옆에 그리는 방법은 이미 있다(`zoom-levels.md` → "Diagram references").
- **선택지:** A. "6. Pick the diagram…"에 한 문장을 넣는다: 맞는 줄이 없으면 알맞은 정석 그림을 고르고 이유를 한 줄로 말한다. 금지 문장 2개를 지운다. 새 줄은 만들지 않는다. B. 그림 종류마다 줄을 만든다(Class 등).
- **추천: A.** 사용자의 원칙과 같다. B는 사용자가 이미 거부한 방향이다("모든 상황마다 규칙 만들자고?").

답을 받으면 "Decisions Made"에 기록하고 "Next Steps" 1번으로 간다.

## Context

- **질문하기 전에 하나만 본다: "이것이 '요청 → 알맞은 그림'을 바꾸나?"** 바꾸지 않으면 묻지 않는다. 원칙이 이미 답하는 것은 규칙으로 만들지 않고 질문으로도 올리지 않는다. 이 세션은 이것을 어겨서 대부분의 시간을 썼다("What Didn't Work").
- **규칙을 만드는 기준(사용자의 원칙):** 모델이 잘 판단하고 결과가 그림에 보이는 선택은 규칙으로 정하지 않는다. 사용자의 말: "모델 에이전트가 잘 판단할텐데 왜 룰을 해야하냐고", "맘에 안들면 사용자가 다시요청하겟지". 에이전트가 덧붙인 경계: 그림에서 **빠진 것**은 사용자가 볼 수 없어서 다시 요청할 수 없다. 그래서 필수요소 목록(`routing-table.md`의 "Required elements")은 남긴다. 사용자는 이 경계에 반대하지 않았다. 명시적으로 승인하지도 않았다.
- **줌인과 줌아웃은 별도의 규칙이 아니다.** 원칙의 한 경우다. 에이전트는 줌인을 별도의 규칙으로 세 번 제안했고 세 번 모두 틀렸다.
- **결정 기록과 규격 적용을 구분한다.** 합의한 결정은 이 핸드오프에 기록한다. 용어는 `CONTEXT.md`에 넣는다. PRD, 스킬, `docs/canvas-guide.md`에는 **후보를 모두 정한 다음 사용자가 지시할 때 한 번에** 반영한다.
- **사용자의 답과 승인이 먼저다.** 사용자가 질문하면 답부터 한다. 파일은 사용자가 승인한 뒤에 고친다.
- **한 번에 한 질문만 한다.** `grilling` 스킬의 라운드 방식보다 사용자의 방식이 우선이다. 질문 전에 그 후보를 먼저 설명한다. 사실 확인은 에이전트가 한다. 질문에는 확인한 사실과 추천 하나를 붙인다.
- 사용자는 ADHD가 있다. 긴 설명을 싫어한다. 결론 한 줄 → 작은 예시나 작은 표 하나 → 질문 하나 순서로 말한다.
- **사용자의 말로 말한다.** 사용자는 "상황", "묶음", "필수요소", "22번째" 같은 우리 문서의 말을 모른다. 처음 쓸 때 한 줄로 뜻을 말한다. 통한 말: "그림 목록", "줄", "칸(레인)", `"주문 취소는 어떻게 갈라져?" → 액티비티 다이어그램` 같은 요청 → 그림 예시.
- 보고의 맨 위에 "사용자의 목표와 풀려는 문제"를 에이전트의 말로 다시 쓴다(사용자가 지정한 형식).
- 사용자는 에이전트의 추천을 그대로 받지 않는다. 근거를 묻는다. 그리고 "내 말이 틀렸어? 틀리면 틀렸다 해"라고 요구한다. 동의하기 전에 원문을 본다. 틀린 것은 틀렸다고 말한다.
- **이번 세션(2026-10-03 네 번째)의 흐름:** 7-②의 질문 3개에 답을 받았다(모두 "에이전트가 판단한다") → 사용자가 "스윔레인은 줄이 아니고 액티비티 다이어그램 안의 한 갈래"라고 했다 → 리서치를 돌렸다 → 사용자가 "DDD 특화"와 애그리거트 내부를 제기했다 → 에이전트가 줌인 규칙을 세 번 제안했다 → 사용자가 최상위 원칙으로 정리했다 → 핸드오프.

### 후보 1: 경로 그림은 진입점에서 시작한다

- 경로 그림에만 진입점 규칙을 적용한다. 정의는 `CONTEXT.md` → "경로 그림". 적용하는 상황은 6개다: API behavior, Authentication and authorization, Retry and branching, Saga, Queue and batch pipeline, Performance bottleneck.
- 현재 코드와 변경안을 한 그림에 담는다. 변경이 크면 현재/변경 후 두 그림을 나란히 둔다. 없어지는 것도 보이게 한다.
- 진입점부터 바뀐 단계 앞의 기존 단계까지 넣는다. HTTP 응답에서 끝내지 않고 이후 처리도 담는다. 판단에 필요 없는 부분은 `…`로 생략했다고 표시한다.
- Whiteboard의 함수 단위 호출 트리는 가져오지 않는다. 줌은 경계 타입(L5)에서 끝난다.
- **변경 상태 색:** 결정과 이유는 ADR-0015에 있다. 색값(연한 채우기): added = `#ebfbee` + 테두리 `#2f9e44`, removed = `#fff5f5` + `#e03131`, modified = `#fff9db` + `#f08c00`. 화살표는 테두리 색을 쓴다. 적용할 때 원본은 `docs/canvas-guide.md` 한 곳에만 둔다(ADR-0006). 다크 모드는 확인하지 않았다.
- **레이어 위반:** L4의 "방향 위반 빨강 표시" 규칙을 뺀다. 에이전트는 위반을 판단하지 않는다. 의존을 그대로 그리고, 사용자가 보고 판단한다. 같이 지울 문장: `plugin/skills/archdraw/references/zoom-levels.md` → "L4: the layer diagram"의 "Violations differ per module…" 문장, `spec.md` → "L4 정의"의 같은 뜻 문장.

### 후보 2: 누가 어느 데이터를 읽고 쓰나

- **근거:** Whiteboard의 `references/whiteboard/packages/review/src/review-api/blocks/database_lens.ts`. 유스케이스 하나가 실제로 읽고 쓰는 저장소와 필드까지 한 그림으로 잇는다. 소유 칸은 없다.
- **규칙(한 줄):** 경로의 한 단계가 데이터를 읽거나 쓰면, 그 단계에 읽기/쓰기와 어느 데이터인지를 적는다. 데이터의 단위는 그 그림의 줌 레벨을 따른다. 새 그림 종류나 새 상황은 만들지 않는다.

### 후보 3: 계약은 경계의 원래 모양대로 캔버스에 쓴다

- **Whiteboard에서 온 것:** 계약은 그림이 아니라 글자로 보여 준다. 그림과 같은 화면에 둔다. 근거: `references/whiteboard/packages/review/instructions/authoring.md`의 "if the change is mostly a new/changed contract, show the key types / interfaces as `code_peek`(s)" 줄, 렌더링은 `references/whiteboard/packages/review/app/src/CodePeek.tsx`. 상태 코드, 에러, 멱등에 대한 규칙은 Whiteboard에 없다.
- **Whiteboard와 다른 점:** Whiteboard는 구현 후의 실제 코드를 잘라서 보여 준다. archdraw는 구현 전이라 잘라 낼 코드가 없다. 그래서 모양을 우리가 정했다.
- **규칙(확정):** 계약은 박스로 그리지 않는다. **주소 + 실제 값 예시**로, 그 경계의 원래 모양대로 캔버스에 쓴다. 종류별 규칙을 따로 만들지 않는다.
  - HTTP: 메서드, 경로, 헤더 + JSON 본문 + 상태 코드별 응답(`→ 200 {...}`, `→ 409 {...}`)
  - 메시지: 토픽, 키 + 페이로드
  - DB: 테이블 + 행 하나
  - Redis: 키 패턴, 타입, TTL + 값
  - 내부 계약(코드 인터페이스, 예: 포트)만 타입 코드다.
- 이 모양이면 기존 필수요소 7개(`spec.md` → "API 계약")가 주석 없이 들어간다. 테이블 사이의 관계는 Data model 상황(ERD)이 그대로 맡는다.
- **용어(확정): 계약.** `CONTEXT.md` → "계약". 피할 말: 스펙, 포맷, 스키마. 적용할 때 상황 이름 "API contract"를 API에 한정하지 않게 넓힌다.
- **캔버스 배치(확정): C안.** 계약 글자를 해당 화살표 옆에 두고, 회색 메모지 배경(`#f1f3f5`, 테두리 없음)으로 묶는다. 본문은 고정폭 글꼴이다. 화살표와 메모지는 같은 번호(①②…)로 잇는다. 노랑 메모지는 변경 상태 색 `modified`와 충돌해서 회색으로 했다(ADR-0015). 옆에 자리가 없을 때만 그림 아래에 모은다.
- 길이 대책: 바뀌는 계약과 쟁점 필드만 놓고 나머지는 `…외 n필드`로 줄인다(`spec.md` → "API 계약"의 그리는 규칙 (2) 그대로).
- 버린 안: 타입 정의 코드로 쓰기, 채팅 텍스트로 보여 주기, 테두리 카드를 아래에 정렬(B안).
- 적용 때 정할 것(에이전트 메모):
  - 스펙의 "코드·쿼리·값·이유는 텍스트"(`spec.md` → "대화 중 사용")에 계약이 예외로 들어간다.
  - 변경안에서 계약이 새로 생기거나 바뀔 때의 표시. 기본은 ADR-0015대로 메모지 배경을 변경 상태 색으로 바꾸고 라벨을 붙이는 것이다. 메모지 안의 한 줄만 바뀐 경우의 표기는 정하지 않았다.
  - 이벤트 메시지 계약의 라우팅. `spec.md` → "API 계약"의 라우팅 예외는 "이벤트 메시지 계약 → 이벤트 토폴로지"다. 공용 규칙에서는 메시지도 계약 메모로 쓴다. 두 문장을 맞춘다.

### 후보 4: 조금씩 그리기는 가져오지 않는다

- **결정: 지금처럼 한 번의 호출로 그린다.** 규격을 바꾸지 않는다. 적용할 것이 없다.
- **이유:** 나눠 그려도 새 오해를 잡지 않는다. 같은 누락을 조금 일찍 보여 줄 뿐이다. 근거는 Whiteboard 지시문 한 줄(`authoring.md`의 "IMPORTANT: Write incrementally." 줄)뿐이고 효과를 잰 자료가 없다. 사용자의 말: "굳이 보여줄 필요가 있나".
- **다시 볼 조건:** 도그푸딩(이슈 02)에서 빈 캔버스를 기다리는 것이 답답하면 3단계 분할(박스 → 화살표 → 글자, 멈추지 않음)을 다시 본다.

### 후보 7 앞부분: 큰 축은 넣지 않는다. 라우팅 표를 목차 + 줄별 파일로 나눈다

- **큰 축(구조 / 시간 / 상태 / 데이터 / 계약)을 넣지 않는다.** 이유: Whiteboard의 축과 archify의 축(`references/archify/archify/SKILL.md` → "Type router")은 렌더러 블록과 스키마의 종류다. archdraw는 자유 캔버스라 고를 렌더러가 없다. 모양을 먼저 고르면 "The question wins over the name"(`plugin/skills/archdraw/SKILL.md` → "6. Pick the diagram from the question")과 반대가 된다.
- **기준(백엔드 질문)은 유지한다.** 틀린 선택은 사용자가 잡는다. 에이전트가 고른 이유를 한 줄로 말하는 규칙이 이미 있다(같은 절의 "Say why, in one line, in chat").
- **`routing-table.md`를 나눈다(점진적 공개).** 지금은 한 줄(약 20줄)을 고르려고 470줄을 읽는다. 바꾼 모양:
  - `plugin/skills/archdraw/references/routing-table.md`: 목차(상황마다 질문 한 줄)와 공통 규칙만 둔다.
  - `plugin/skills/archdraw/references/rows/<상황>.md`(새로 만든다): 줄의 상세. 7-①의 결정으로 파일 수는 21개가 아니라 23개다.
  - 모델은 목차로 고르고, 고른 줄의 파일만 읽는다.
- **줄의 내용은 지금 줄이지 않는다.** 줄이는 일은 도그푸딩(이슈 02) 뒤에 한다.
- **근거(위키):** `wiki/summaries/claude-code-skills-lessons.md` → "3. 진입점은 맵으로 쓰고 세부 자료는 분리한다", "2. 지식은 반복 실패 지점에 집중한다". `wiki/concepts/progressive-disclosure.md` → "소스별 시각" 표(이전 세션의 기록, 다시 읽지 않음).
- **가져오지 않는 것:** archify의 `guide`(`references/archify/archify/recipes/scenarios.mjs` → `scoreRecipe()`, `recommendScenario()`).
- **열린 것:** `plugin/skills/archdraw/SKILL.md`가 296줄이다. 줄일지는 보지 않았다.

### 후보 7 뒷부분: 볼 범위는 Class와 Activity 두 칸이다

- **확정(사용자 승인, 이전 세션):** 실무 4종(Class, Sequence, Activity, Deployment)을 빈칸 2개(Class, Activity)의 근거로 쓴다. 기준은 80/20이다. 나머지 6개(Composite structure, Object, Profile, Use case, Communication, Interaction overview)는 넣지 않는다.

| 구조 7 | 우리 | 행위 7 | 우리 |
|---|---|---|---|
| Class | 없음 | Activity | 일부: Incident response flow |
| Component | 비슷: System overview | Use case | 없음 |
| Composite structure | 없음 | State machine | 있음: Saga, Retry and branching, Entity lifecycle |
| Deployment | 있음: Deployment map | Sequence | 있음: API behavior, Authentication and authorization |
| Object | 없음 | Communication | 없음 |
| Package | 비슷: System overview | Interaction overview | 없음 |
| Profile | 없음 | Timing | 비슷: Concurrency and locks |

- 14개의 이름은 UML 2.5.1 Annex A 원문에서 확인했다. "우리" 칸은 에이전트의 판단이다.
- 출처와 확인 수준은 이전 핸드오프의 기록이다. 실무 4종은 사용자가 붙여 넣었고 출처 미상이다. Visual Paradigm 글(https://www.visual-paradigm.com/guide/case-study-uml-2-5-1-the-maturation-of-a-universal-modeling-standard/)은 벤더 글이고 출처 인용이 없다(`research-activity-swimlane.md` → "2.1"). Booch 인용 "For 80% of all software, only 20% of UML is needed."는 그 글에 있다.

### 후보 7-①: 요청 2개를 그림 목록에 추가한다. 그림은 액티비티 다이어그램이다

- **결정(이전 세션): 상황 2개를 추가한다.** 합치지 않는다. 질문이 다르다.

| | 사용자가 이렇게 물을 때 | 답하는 질문 |
|---|---|---|
| 업무 규칙의 갈래 | "주문 취소는 배송 상태에 따라 어떻게 갈라져?" | 어떤 조건에서 어느 길로 가나 |
| 배포 절차 | "이 변경은 어떻게 운영에 나가?" | 변경이 어떤 관문을 거쳐 운영에 나가나 |

- **고친 것(이번 세션):** 그림의 이름은 "스윔레인 플로우"가 아니고 **액티비티 다이어그램**이다. 레인(칸)은 그 안의 선택 사항이다. 사용자의 말: "스웜레인은 뭔가 라우팅 룰에 포함될게 아니라 액티비티 다이어그램 안에 한갈래로 해야하는거아냐?". 리서치가 지지한다(아래 "리서치").
- **이름은 정하지 않았다.** "업무 흐름"은 에이전트가 붙인 임시 이름이고 사용자에게 통하지 않았다. 이름은 보이는 것이고 바꾸기 쉬워서 적용 때 에이전트가 정한다. 사용자에게 묻지 않는다.
- **합의에 쓴 장면:** 주문 취소 3갈래. 배송 전 → 전액 환불. 배송 중 → 회수 요청 → 환불. 배송 완료 → 반품 접수.
- **배포 절차의 재료:** archify `delivery-workflow`(MIT, `references/archify/archify/recipes/scenarios.mjs`). 이 빈칸은 이전에 두 번 미결로 적혀 있었다(`research-structure.md`의 "배치도 × (배포 파이프라인)" 줄, `review.md`의 "빠진 행 후보" 줄).
- **에이전트의 제안(사용자가 승인하지 않았다. 반대하지도 않았다):**
  - 업무 규칙의 갈래에 예외 2개를 붙인다. 조건이 여러 개 조합되면 그림 대신 표로 쓴다(Fowler). "어느 상태에서 되나"는 Entity lifecycle로 보낸다.
  - 배포 절차는 유지한다. 근거가 약하므로 도그푸딩(이슈 02)에서 쓸모를 확인한다.
  - 넣는 곳: 업무 규칙의 갈래는 `routing-table.md`의 "Request" 아래, 배포 절차는 "Operations" 아래.
  - 필수요소, 라우팅 예외는 정하지 않았다.

### 후보 7-②: 스윔레인에 규칙을 만들지 않는다. 에이전트가 판단한다

- **결정:** 레인의 기준, 방향, 컨텍스트 표기는 에이전트가 요청에 맞게 고른다. 규칙으로 적지 않는다. 사용자의 답: 기준 "B가 해야지"(에이전트가 고른다), 방향 "이것도 C지"(에이전트가 고른다).
- **컨텍스트:** DDD이면 컨텍스트 테두리가 레인을 묶는다. 사용자의 말: "ddd면 b잖아". 박스에 쓰는 "DDD 매핑"(`spec.md` → "DDD 매핑")과 같은 모양이다. 헥사고날이면 레인의 이름이 adapter-in / application / domain / adapter-out이다(사용자의 말: "헥사고날 아키텍처도 저렇게 봐도 되는거고").
- **스윔레인은 공통 규칙이 아니다.** 에이전트가 "칸으로 나누기는 모든 그림의 공통 표기다"라고 제안했다가 리서치 뒤에 철회했다. UML에서 스윔레인은 액티비티 다이어그램에만 있다. 구조 그림의 묶음은 다른 것이다(Package, Node 중첩, boundary). 구조 그림의 컨텍스트 테두리는 이미 있어서 더할 것이 없다.
- **확인한 사실:** `docs/canvas-guide.md`는 이미 그림마다 흐름 방향을 에이전트에게 맡긴다("Decide the flow direction for this diagram — top-to-bottom or left-to-right"). 기존의 `routing-table.md` → "Incident response flow"는 역할별 가로 레인을 쓴다. 이 줄은 바꾸지 않는다.
- **알아야 할 것:** 레이어를 레인으로 쓴 예시는 어느 출처에도 없다. UML은 금지하지 않는다(`research-activity-swimlane.md` → "2.3").

### 리서치: 액티비티 다이어그램과 스윔레인 (이번 세션)

파일: `.scratch/archdraw-skill/research-activity-swimlane.md`. 리서치 에이전트가 썼고 메인 에이전트가 전부 읽었다. 결론 표는 그 파일의 "1. 결론 표"에 있다. 결정에 쓴 것만 적는다.

- 액티비티 다이어그램은 업무 갈래에 맞다. 단순한 갈래까지다. 조건이 복잡하면 결정표가 낫다(Fowler *UML Distilled* 3판 1장).
- 액티비티 다이어그램이 배포 절차의 그림이라는 1차 출처는 없다. 배포 파이프라인의 원전(Humble·Farley)은 단계 상자와 시퀀스로 그렸다.
- 레인은 선택 사항이다(UML 2.5.1 §15.6.3.1). "누가 하나"가 쟁점일 때 쓴다.
- 확인하지 못한 것은 그 파일의 "4. 확인하지 못한 것"에 있다(Fowler 3판 11장 본문, 명세 PDF 안의 그림 등).
- **이전 핸드오프의 틀린 출처:** "C4 공식 문서에는 스윔레인이 없다"의 출처를 `research-structure.md`로 적었다. 그 파일에 그 문장이 없다. 사실 자체는 이번 리서치가 확인했다(같은 파일 → "2.4").

### 후보 7-③과 DDD: 방향만 정해졌다 (이번 세션)

- **사용자의 말:** "ddd 특화로 좀 하는게 좋은데". "애그리거트 내부는 그려달라고하면 그려줘야하는데?". "다이어그램에 맞게 그리되 … 개념에 맞게 그리되 줌인 해서 더그려달라고하면 그려줘야지". "애그리거트 내부는 클래스 다이어그램 머 이런거아냐?".
- **정해진 방향:** 애그리거트의 안쪽을 요청하면 클래스 다이어그램으로 그린다. 이것은 별도의 줌인 규칙이 아니고 최상위 원칙의 한 경우다.
- **사용자가 거부한 것:** 애그리거트 내부를 위한 새 줄 + 필수요소 목록("모든 상황마다 규칙 만들자고?"). "기본은 나열하지 않는다"라는 문장(금지처럼 읽힌다).
- **사용자가 고친 것:** "커맨드 → 애그리거트 → 이벤트의 흐름"은 DDD 특화가 아니고 일반적인 상황이다. 기존 줄이 답한다(API behavior, Event topology, Event sourcing).
- **지금 있는 DDD 지원**(`plugin/skills/archdraw/references/zoom-levels.md` → "DDD mapping"): 컨텍스트 경계, 컨텍스트 관계의 화살표 라벨, 헥사고날 레인, «aggregate» 스테레오타입.
- **열린 것:** 적용 방법(First Action의 질문). "DDD 특화"가 애그리거트 내부 말고 무엇을 더 뜻하는지는 사용자가 말하지 않았다. 에이전트가 먼저 묻지 않는다. 사용자가 다시 꺼내면 다룬다.

### 글꼴 (이전 세션)

- **기본 글꼴을 손글씨체에서 바꾼다.** 어느 글꼴로 바꿀지는 정하지 않았다. 예시 그림에서는 `helvetica`를 썼다.
- 사실: 서버 기본값이 손글씨체다(`src/core/expand-elements.ts`의 `normalizeFontFamily(rest.fontFamily) ?? 1`). `docs/canvas-guide.md`에는 글꼴 종류 규칙이 없다(이전 세션의 기록).

## What Worked

- **요청 → 그림 예시.** `"주문 취소는 어떻게 갈라져?" → 액티비티 다이어그램` 같은 한 줄이 추상적인 설명보다 통했다.
- **같은 흐름을 두 방법으로 나란히 그린 작은 그림.** "스윔레인을 무엇으로 나누나"는 통하지 않았다. 칸 2종을 ASCII로 나란히 놓은 뒤에 통했다.
- **사용자가 "장황하다"고 하면 세 줄로 다시 말했다.** 통했다.
- **리서치를 백그라운드 에이전트에 맡기고 반대 근거를 요구했다.** 에이전트가 반대 근거(Fowler의 결정표, Camunda)와 이전 기록의 틀린 출처를 찾았다. 결과 파일의 모든 인용에 절 번호와 확인 수준이 있다.
- **틀린 것을 틀렸다고 말했다.** 사용자가 요구한 것이다. 에이전트의 추천 A(방향 고정)와 "공통 표기" 제안을 철회했을 때 사용자가 바로 다음으로 갔다.
- 이전 세션에서 계속 유효한 것: 캔버스에 실제 예시를 여러 벌 그려서 고르게 한다. "Whiteboard에서 온 것"과 "내가 더한 것"을 나눠서 말한다. 근거를 물으면 방어하지 않고 원문을 다시 확인한다.

## What Didn't Work

- ⚠️ **목표가 아니고 핸드오프의 할 일 목록을 따라갔다.** 레인의 방향, 줄의 이름 같은 질문을 그대로 물었다. 원칙이 이미 답하는 질문이었다. 사용자의 말: "근데 왜 자꾸 헛소리를해?". 질문 전에 "이것이 '요청 → 알맞은 그림'을 바꾸나?"를 본다.
- ⚠️ **경우마다 규칙이나 새 줄을 제안했다.** 방향 고정, 줌인용 새 줄, "기본은 나열하지 않는다", "줌인을 요청하면…". 사용자의 말: "모델 에이전트가 잘 판단할텐데 왜 룰을 해야하냐고", "모든 상황마다 규칙 만들자고?".
- ⚠️ **확인하기 전에 "맞다"고 했다.** "시스템 오버뷰도 스윔레인을 쓸 수 있다"에 동의하고 "공통 표기"로 넓혔다. 리서치 뒤에 뒤집었다. 동의하기 전에 원문을 본다.
- ⚠️ **에이전트가 만든 말을 설명 없이 썼다.** "22", "23", "업무 흐름", "상황", "묶음", "공통 표기", "필수요소". 사용자가 매번 뜻을 물었다. 한 그림에 이름 2개("스윔레인 플로우", "액티비티 다이어그램")를 섞어 썼다.
- ⚠️ **또 장황했다.** 사용자의 말: "장황하게말하지마 머라고?". 사과와 근거의 나열을 빼고 결론부터 말한다.
- **같은 "기록하나?"를 여러 번 물었다.** 내용이 틀려서 답이 오지 않은 것이었다. 답이 없으면 질문이 아니고 내용을 의심한다.
- **부정확한 말.** "796쪽을 읽는다"(필요한 절만 읽게 했다), "없다"(커맨드 → 이벤트의 흐름. 기존 줄이 답한다).
- 이전 세션의 교훈(계속 유효): 답보다 먼저, 승인 없이 파일을 고치지 않는다. 사용자가 준 자료는 원문을 직접 읽고, 무엇을 채택하는지 먼저 말한다. 추천 전에 원본과 **우리 기록**을 확인한다. 개수는 목록을 세고 말한다. 질문 앞에 "후보 N: 이름"을 말하되 그 이름의 뜻도 말한다. 사용자가 다른 주제로 가면 그 주제를 따라간다. 스킬의 구조나 분량을 추천하기 전에 `wiki/index.md`에서 스킬 작성 지식을 확인한다. 그림에 글꼴을 지정한다.
