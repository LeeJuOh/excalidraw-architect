## Problem Statement

백엔드 개발자가 AI 에이전트와 코드 작업을 할 때 **텍스트로는 아키텍처가 통하지 않는다.** 에이전트가 텍스트로 구조를 설명하면 이해가 안 가고, 내가 원하는 큰 그림을 텍스트로 설명하면 에이전트가 오해한다. 그래서 그림을 그려가며 그릴하고 있고, 도구로 yctimlin의 라이브 Excalidraw 캔버스를 쓴다.

도구는 충분하다. 캔버스는 양방향이라 내가 브라우저에서 직접 고치면 에이전트가 스크린샷으로 읽는다. 부족한 건 **판단**이다:

- 에이전트가 **뭘 그릴지** 기본값으로 흐른다. "이 API 부르면 뭐가 일어나"를 물어도 박스-화살표 컴포넌트 그림을 그린다.
- **줌 레벨을 섞는다.** 서비스 그림에 클래스 이름이 들어가고, 한 그림에 구조와 시간축이 같이 있다.
- **내가 고친 걸 뒤엎는다.** 캔버스에서 박스를 옮겨놓으면 다음 턴에 재배치한다.
- 아키텍처 외 실무 상황(장애 분석, 락 문제, 마이그레이션, API 계약)에 어떤 그림이 맞는지 기준이 없다.

기존 자산 두 개가 이 판단을 주지 않는다:

- **yctimlin MCP** — 손. 캔버스 조작 전부 + 치수·색 규격(`read_diagram_guide`). "무엇을 그릴지"는 없다.
- **excalidraw-diagram-skill** — 눈썰미. "잘 그리는 법" 방법론 552줄. 설명·교육용 그림에 최적화돼 있어 일부 원칙은 아키텍처 도면과 정면 충돌한다(균일 금지, 박스 최소화). 렌더러는 yctimlin이 대체한다.

## Solution

yctimlin 캔버스 위에서 동작하는 **판단 전용 스킬.** 네 가지를 준다:

1. **상황 → 그림 라우팅.** 백엔드 실무 21개 상황마다 답하는 질문 한 문장, 그림 종류, 필수요소를 정한다.
2. **캔버스 우선.** 에이전트는 행동 전에 캔버스를 보고, 내가 바꾼 건 뒤엎지 않는다. 텍스트 설명 없이 그림으로 왕복.
3. **줌 레벨과 연결.** 시스템 → 배포 단위 → 모듈 → 레이어 → 경계 타입. 확대는 실제 구조를 따르며, 중복 단계 생략과 공용 모듈 그림의 공유 참조를 허용한다. 레벨은 스택과 무관하며, 근거 추출은 선언 파일 → 디렉터리 관례 → import 추론 순서로 한다. 선언 파일은 의존 관계의 근거이고, 호출·구독·실패 처리 관계는 해당 코드가 근거다.
4. **모드.** 기본은 안 남김(설명 그림). 내가 말하면 도면으로 승격 → 지정한 경로에 저장. 산출물 저장 경로는 고정하지 않는다.

**범위 밖 (2026-09-19 2차 검수 C):** archdraw는 그림으로 설명하고 사용자 교정·결정을 캔버스에 반영하는 데서 끝난다. 결정의 이유·합의 기록은 사용하는 프로젝트의 문서 규약(PRD·이슈·ADR) 몫이며, 그림은 거기서 참조하는 보조 자료다. 그림 안 결정 기록 기능·자동 ADR 생성·별도 인계 시스템은 만들지 않는다. 이 경계는 구현 범위 표시이며 SKILL.md 지시로 적지 않는다.

## User Stories

1. As a 백엔드 개발자, I want "이 API 부르면 뭐가 일어나"를 물으면 시퀀스 다이어그램이 나오기를, so that 컴포넌트 그림을 받고 다시 요청하지 않는다.
2. As a 백엔드 개발자, I want "구조가 어떻게 돼"를 물으면 시스템 개요 그림(줌 레벨)이 나오기를, so that 큰 그림부터 본다.
3. As a 백엔드 개발자, I want 서비스 레벨 그림에 클래스 이름이 안 들어가기를, so that 서비스 5개짜리 그림이 클래스 40개로 터지지 않는다.
4. As a 백엔드 개발자, I want 한 그림에 구조와 시간축이 섞이지 않기를, so that 그림 하나가 한 질문에 답한다.
5. As a 백엔드 개발자, I want 박스 라벨이 "인증 API"가 아니라 `POST /auth/token`이기를, so that 그림만 보고 코드를 찾는다.
6. As a 백엔드 개발자, I want 캔버스에서 박스를 옮겨놓으면 에이전트가 그 배치를 정답으로 받기를, so that 좌표를 텍스트로 설명하지 않는다.
7. As a 백엔드 개발자, I want 캔버스에 남긴 표시(어떤 색·모양이든)를 에이전트가 고칠 곳으로 읽기를, so that "왼쪽 위에서 세 번째"라고 말하지 않는다.
8. As a 백엔드 개발자, I want 반영된 표시를 에이전트가 정리하기를, so that 캔버스에 처리된 피드백이 쌓이지 않는다.
9. As a 백엔드 개발자, I want 손그림 사진이나 대충 그린 초안을 던지면 정식 그림으로 옮겨주기를, so that 초안을 말로 설명하지 않는다.
10. As a 백엔드 개발자, I want "order-service 내부 보여줘"라고 하면 이미 그린 모듈 그림을 보여주고, 없으면 그려주기를, so that 지도처럼 줌인한다.
11. As a 백엔드 개발자, I want 모듈 의존성이 `build.gradle`이나 `@Module({imports})`에서 읽히기를, so that 에이전트가 추측하지 않는다.
12. As a 백엔드 개발자, I want 추론으로 그린 의존성이 점선으로 구분되기를, so that 확실한 것과 추정을 구분한다.
13. As a 백엔드 개발자, I want Gradle이든 NestJS든 같은 줌 레벨 정의를 쓰기를, so that 스택이 바뀌어도 그림 읽는 법이 같다.
14. As a 백엔드 개발자, I want 그림이 기본으로 저장되지 않기를, so that 일회성 이해 그림이 레포를 오염시키지 않는다.
15. As a 백엔드 개발자, I want "저장해"라고 하면 원하는 경로에 파일로 저장하고 저장 위치를 알려주기를, so that 다음 세션 에이전트가 그 파일을 읽고 이어간다.
16. As a 백엔드 개발자, I want "다듬어줘"라고 하면 정렬·색·범위가 도면 수준으로 올라가기를, so that 버릴 그림을 남길 그림으로 승격한다.
17. As a 백엔드 개발자, I want 저장된 도면을 복사해 그 위에 변경안을 색칠할 수 있기를, so that before/after를 비교한다.
18. As a 백엔드 개발자, I want 장애 원인을 파볼 때 타임라인 그림이 나오기를, so that 어디서 끊겼는지 시각별로 본다.
19. As a 백엔드 개발자, I want 락·동시성 문제를 볼 때 트랜잭션 경계와 락 획득 순서가 그려지기를, so that 데드락 사이클을 눈으로 찾는다.
20. As a 백엔드 개발자, I want 성능 병목을 볼 때 구간별 레이턴시 분해가 나오기를, so that 어디가 전체의 몇 %인지 안다.
21. As a 백엔드 개발자, I want 재시도 정책 그림에 백오프 간격과 최대 횟수가 반드시 있기를, so that 그림만 있고 판단은 못 하는 일이 없다.
22. As a 백엔드 개발자, I want 마이그레이션 계획에 단계별 전환·이중쓰기 구간·롤백 지점이 그려지기를, so that 계획을 팀에 그림으로 보여준다.
23. As a 백엔드 개발자, I want 이벤트 토폴로지에 토픽명·발행자·구독자·순서보장 여부가 있기를, so that "이 이벤트 누가 받아"에 답한다.
24. As a 백엔드 개발자, I want API 계약 그림에 실제 요청/응답 페이로드가 있기를, so that 협의 중 "예를 들면"이 필요 없다.
25. As a 백엔드 개발자, I want 설명용 그림에선 배치가 의미를 말하기를(팬아웃은 퍼지는 모양), so that 텍스트를 지워도 구조가 읽힌다.
26. As a 백엔드 개발자, I want 도면에선 같은 역할이 같은 모양이기를, so that `order-service`를 3초 안에 찾는다.
27. As a 백엔드 개발자, I want 에이전트가 애매하면 "구조야, 흐름이야?"라고 되묻기를, so that 잘못된 그림에 시간을 쓰지 않는다.
28. As a 백엔드 개발자, I want 그리기 전에 에이전트가 실제 코드를 읽기를, so that 그림이 스펙이 아니라 코드를 반영한다.
29. As a 백엔드 개발자, I want 에이전트의 텍스트 설명이 이해 안 될 때 `/archdraw`를 부르면 방금 설명이 그림으로 나오기를, so that 텍스트를 다시 읽지 않는다. (2026-09-12 그릴)
30. As a 백엔드 개발자, I want 내 설명을 에이전트가 오해했을 때 `/archdraw 네가 이해한 대로 그려봐`로 그리게 하고 캔버스에서 고치면 에이전트가 그 편집의 뜻(교정·제안·결정)대로 이어가기를, so that 오해를 말로 다시 풀지 않는다. (2026-09-12 그릴, 2026-09-19 2차 검수 A2로 "고친 그림이 정답" 표현 교체)
31. As a 백엔드 개발자, I want 한 번 부른 뒤 같은 대화에서 연결·순서가 들어간 답("부분 환불은 어떻게 흘러가?")은 에이전트가 먼저 그림으로 답하기를, so that 매번 다시 부르지 않는다. (2026-09-12 그릴)
32. As a 백엔드 개발자, I want 변경안을 논의할 때 지금 구조 그림 위에 바뀌는 부분만 새 색으로 보이기를, so that 무엇이 바뀌는지 한눈에 본다. (2026-09-12 그릴)

## Implementation Decisions

**플러그인 형태** (2026-09-11 그릴 확정)
- yctimlin 포크(MIT) 레포 = 캔버스 서버(우리 코드) + 스킬 1개 + 플러그인 패키징. 내장 `excalidraw-skill`은 판단 스킬로 교체, 조작법은 `references/canvas-ops.md`로 이동.
- 인터페이스: **CLI 기본**(yctimlin CLI 그대로; JSON stdout, 스크린샷은 파일→Read). MCP는 옵션. **호출 줄 (2026-09-11 3차 확정, 검수 R01로 수정)**: `skills/archdraw/scripts/archdraw` shim을 두고 SKILL.md는 `scripts/archdraw <cmd>`로 부른다(스킬 루트 기준 상대경로 — Agent Skills 스펙 관례). shim은 셸 몇 줄: `ARCHDRAW_BIN`이 있으면 `exec node "$ARCHDRAW_BIN" "$@"`(개발자 로컬 빌드), 없으면 `exec npx -y excalidraw-architect@<버전> "$@"`(npm 게시본, 버전은 7-5b가 생성). 이유: Codex는 SKILL.md 안 `${CLAUDE_PLUGIN_ROOT}`·`${PLUGIN_ROOT}`를 치환 안 함(Agent Plugins §9.2, 치환은 mcp.json args/env/cwd만), 반면 스킬 폴더 경로는 Claude("Base directory")·Codex(스킬 목록에 파일 경로) 둘 다 모델에 알려줌. 구 `node ${CLAUDE_PLUGIN_ROOT}/dist/bin.js`와 구 shim의 `dist/bin.js` 직접 실행은 폐기 — `dist/`는 gitignore이고 플러그인 설치는 복사(+Claude는 `npm ci --ignore-scripts`)만 해서 새 PC엔 실행 파일이 없다. `allowed-tools`는 Claude용 `Bash(${CLAUDE_SKILL_DIR}/scripts/archdraw *)`(Codex는 무시, 무해). 대안 기각: 빌드 결과 커밋(Codex는 의존성 설치 보장이 없어 서버 번들 작업이 추가됨) / 첫 호출 때 shim이 빌드(실패 지점이 사용자 PC의 네트워크·node·빌드 시간으로 이동) / SessionStart 훅이 루트 경로 파일에 기록(Codex 훅은 v1 스펙 밖 + 두 벌).
- **첫 실행 안내** (검수 R01): 스킬은 첫 턴 서버 명령 전에 "캔버스 서버 준비 중, 처음이면 다운로드로 오래 걸림" 한 줄을 알린다. 실패하면 에러를 원인(인터넷 없음·Codex 권한)으로 옮겨 알린다. shim이 캐시 여부를 판단하지 않는다(로직 불필요). README에 "첫 실행에 인터넷 필요" 한 줄.

*saga · CQRS · 이벤트 소싱*
- **saga(분산 작업 실패 복구)** — 질문: 여러 서비스에 걸친 작업이 중간에 실패하면 무엇을 되돌리고 무엇을 끝까지 밀어붙이나? · 그림: 상태도 — 노드는 단계와 담당 서비스, 실패 전이는 보상 체인으로 합류, 종료 상태(성공·보상 완료·수동 개입) 전부 표시 · 필수요소: ① 조율 방식과 진행 상태 저장 위치 ② 단계 분류(보상 가능·pivot·재시도) ③ 보상 동작·순서·범위 ④ 실패 판정과 복구 경로(거절·결과 모름·보상 실패) ⑤ 격리 부재 대응 · 라우팅 예외: 보상 없이 재시도만 → 재시도·분기.
- **CQRS(읽기·쓰기 모델 분리)** — 질문: 명령과 조회가 어떤 모델·저장소로 갈라지고, 조회는 쓰기 결과를 언제부터 보나? · 그림: 박스-화살표 — 명령·조회 두 칸, 쓰기→읽기 동기화 화살표에 시점·수단 라벨 · 필수요소: ① 분리 수준(코드·경로만 / 모델 분리·저장소 하나 / 저장소 분리) ② 명령 응답 방식과 거절 지점 ③-a 동기화 시점(동기·같은 트랜잭션 / 비동기 / 실시간 계산) ③-b 동기화 수단(앱 코드 / DB 트리거·뷰 / 메시지 큐·이벤트 스트림 / CDC / 배치) ④ 반영 지연 허용치와 stale 읽기 대응 ⑤ 읽기 모델 재구축 경로 · 그리는 규칙: ①이 코드·경로만이면 ③④⑤는 "없음 확인", 동기화 화살표 안 그림 · 라우팅 예외: 명령 쪽 분리 없이 읽기 복제본만 → 저장소 토폴로지 · 02 재판정: 질문이 "읽기 DB 언제 반영돼?"로만 나오면 행 삭제 + 데이터 흐름 행에 ⑤ 추가; ③-b 값 중 한 번도 안 나온 것 제거.
- **이벤트 소싱(이벤트 기록으로 상태 저장)** — 질문: 이 엔티티의 상태는 어떤 이벤트 기록으로 남고, 그 기록에서 현재 상태를 어떻게 다시 만드나? · 그림: 박스-화살표 — 명령 처리기 → 이벤트 스토어(스트림 하나를 버전 붙은 이벤트 칸으로) → 구독자(프로젝션·외부 연동) · 필수요소: ① 스트림 경계와 이벤트 이름 ② append 경로와 동시 쓰기 충돌 처리 ③ 상태 복원 방식(전체 리플레이 / 스냅샷) ④ 이벤트 스키마 변경 대응 ⑤ 리플레이 때 외부 부작용 차단 · 라우팅 예외: 원본이 상태 DB이고 이벤트가 outbox·CDC로 파생 → 이벤트 토폴로지·데이터 흐름 · 02 제거 후보: ③④("확인 못 함"만 남으면).

*요청*
- **API 동작** — 질문: 이 요청은 누가 누구를 어떤 순서로 부르고, 무엇을 돌려주며, 실패하면 어디로 갈라지나? · 그림: 시퀀스 — 참여자 머리 상자+세로선, 실행 구간, 조건 갈래 `alt`/`opt` + `[조건]` · 필수요소: ① 호출자·피호출자 ② 요청·응답(이름·주요 인자·상태 코드) ③ 메시지별 동기/비동기 ④ 실패·대체 경로(성공·실패·결과 모름 3갈래) ⑤ 비동기 후속(202+Location+Retry-After·큐·백그라운드 작업·완료 통지·재시도·타임아웃 — 동기 API면 "없음 확인") ⑥ 호출별 타임아웃·마감 · 라우팅 예외: 보상이 붙으면 → saga / 한 호출의 재시도 수치 → 재시도·분기 / 페이로드 모양 → API 계약 / 인증 자체가 질문 → 인증·권한 · 화살표 표기는 §3의 "선 표기"를 따른다 · 02 제거 후보: ⑥.
- **인증·권한** — 질문: 이 요청의 자격은 누가 발급·검증하고, 언제 만료되며, 만료·부족하면 무엇이 돌아오나? · 그림: 시퀀스 + 신뢰 경계 — 경계를 세로 띠로, 띠를 넘는 메시지에 검사 표시(UML에 기호 없음, 캔버스 근사형) · 필수요소: ① 참여자와 발급·검증 주체 ② 자격 증명 종류와 전달 방식 ③ 수명(토큰 `exp`·세션 idle/absolute) ④ 갱신·재인증 시점 ⑤ 만료·거부 응답(401·403)과 그 뒤 흐름 ⑥ 권한 검사 지점과 규칙(역할×권한 표는 노트 한 줄) ⑦ 신뢰 경계 · 라우팅 예외: 인증이 답이 아니면 → API 동작(인증 서버는 참여자 하나로만) / 경계가 어디냐 → 시스템 개요(이 행은 넘을 때 무엇을 검사하나) / 필요 스코프만 → API 계약 · 02 제거 후보: ⑦.
- **API 계약** — 질문: 이 엔드포인트는 무엇을 받고 무엇을 돌려주며, 에러와 버전은 어떻게 약속돼 있나? · 그림: **표준 표기 없음(OpenAPI·AsyncAPI·Pact 전부 문서 구조만) — 캔버스 근사형**: 박스 하나에 구역 3개(머리: 메서드+경로·버전·스코프·멱등키 / 요청·응답 상자에 실제 페이로드 / 에러 표: 코드·상태·본문 형식). 서비스 간 제공/필요 관계를 보일 때만 UML lollipop/socket. 줌 레벨과 별개의 그림 종류. **02 최우선 검증 대상** · 필수요소: ① 엔드포인트·오퍼레이션 식별 ② 실제 요청 페이로드 ③ 실제 응답 페이로드와 상태 코드 ④ 에러 코드와 에러 본문 형식 ⑤ 버전 정책과 호환성 규칙 ⑥ 필요한 인증·스코프 ⑦ 멱등·재시도 계약 · 그리는 규칙(02 시험용 초안): (1) 구역 3개 고정, 에러 5행 넘으면 "외 n건" (2) 페이로드는 쟁점 필드만 + `…외 n필드`, "전체로" 하면 그 상자만 펼침 (3) ⑤⑥⑦이 "없음 확인"이면 머리에 안 씀; 협의 중 계약은 `설계` 태그, 실선+새 색 · 라우팅 예외: 호출 순서 → API 동작 / 저장 스키마 → 데이터 모델 / 이벤트 메시지 계약 → 이벤트 토폴로지 · 02 제거 후보: ⑦; 사용자가 매번 텍스트로 바꾸면 그림 종류 자체를 텍스트 산출물로 전환.
- **재시도·분기** — 질문: 이 호출이 실패하면 무엇을 다시 하고, 몇 번·얼마 간격으로 하며, 포기하면 어디로 보내나? · 그림: 상태도(UML 기호 — 둥근 사각형, 전이 라벨 `트리거 [조건] / 동작`, 시작 채운 원, 종료 이중 원, 갈래 마름모) · 필수요소: ① 재시도 대상 조건(재시도 vs 즉시 실패, 타임아웃 포함) ② 백오프(초기 간격·배수·상한·지터, `Retry-After`도 값) ③ 최대 횟수와 계층 중복 여부 ④ 포기 후 경로(폴백 응답·DLQ·수동) ⑤ 차단 장치(서킷브레이커 상태·재시도 예산·스로틀) ⑥ 재시도 안전성(멱등) · 라우팅 예외: 보상이 붙으면 → saga / 엔티티 상태 집합 → 엔티티 생명주기 / 컨슈머 전체 DLQ 지형 → 이벤트 토폴로지 · 02 제거 후보: ③의 계층 중복(값 못 채우면), ⑥(API 계약 ⑦과 항상 복사면 합침).
- **엔티티 생명주기** — 질문: 이 엔티티는 어떤 상태를 거치고, 무엇이 상태를 바꾸며, 어떻게 끝나나? · 그림: 상태도(UML 기호 그대로; 종료 상태 = 나가는 화살표 없는 상태) · 필수요소: ① 시작·진행 상태 ② 전이 트리거와 조건(가드) ③ 대기·재시도 상태 ④ 모든 종료 상태(순환형 생명주기면 "없음 확인") ⑤ 되돌릴 수 없는 전이·복귀 불가 표시(문장으로 — 안 그린 전이가 곧 불가 전이라 따로 그리지 않음) · 라우팅 예외: 실패 시 되돌림·전진 → saga / 상태를 이벤트로 저장·복원 → 이벤트 소싱 / 한 호출의 재시도 수치 → 재시도·분기 / 지속 상태 없이 참여자 상호작용 → API 동작 · 02 제거 후보: ⑤(④의 노트 한 줄로 합침); 02 관찰: "모든 종료 상태" 강제가 실무 그림보다 무거운지.

*비동기 · 데이터*
- **이벤트 토폴로지** — 질문: 이 이벤트를 누가 발행하고 누가 받으며, 실패하면 어디로 가나? · 그림: 박스-화살표 토폴로지 — 발행자·토픽·구독자 세 열, 토픽 박스에 순서 단위, 실패 경로(재시도 채널·DLQ)는 옆으로 빠지는 화살표, **시간축 없음** · 필수요소: ① 토픽·채널 이름과 이벤트 이름 ② 발행자 ③ 구독자와 컨슈머 그룹 ④ 순서 보장 단위(파티션·ordering key·FIFO — 예/아니오가 아니라 키) ⑤ 전달 보장과 중복 대응(at-most/least/exactly-once + outbox·멱등키) ⑥ 실패·재처리 경로(재시도 채널 ≠ DLQ, 되감기 포함) ⑦ 상태 저장소 ⑧ 페이로드 패턴: Event Notification / Event-Carried State Transfer(full state) / Event-Carried State Transfer(delta) — 패턴 이름 + 쟁점 필드, 전체 스키마 안 그림; Notification이면 구독자→발행자 되부르는 화살표가 생김 · 라우팅 예외: 시간순 → API 동작 ⑤ / 실패 시 되돌림 → saga / 원본이 이벤트 스토어 → 이벤트 소싱 / 적체·처리 속도 → 큐·배치 파이프라인 · 02 제거 후보: ⑧.
- **큐·배치 파이프라인** — 질문: 이 처리는 어디서 막히고, 얼마나 밀렸으며, 실패한 건은 어떻게 다시 도나? · 그림: 파이프라인 그래프 — 노드 = 처리 단계, 엣지 = 단계 사이 흐름, 노드에 병렬 수, 엣지에 적체·처리량 라벨 · 필수요소: ① 처리 단계와 순서 ② 실행·재시작 단위(어디부터 다시 도나) ③ 처리량과 적체 ④ 병렬 단위와 그 상한 ⑤ 백프레셔·흐름 제어(기제 없는 큐는 "없음 확인"이 정답) ⑥ 실패 처리와 재처리 경로(재시도 / DLQ / 선별 재처리) ⑦ 멱등성 · 라우팅 예외: 저장소·원본이 쟁점 → 데이터 흐름 / 토픽 소유·구독자 → 이벤트 토폴로지 / 단계 하나의 백오프·횟수 → 재시도·분기 / 한 요청의 시간 분해 → 성능 병목 · 02 제거 후보: ⑤ · 02 재판정: 큐·배치 × 데이터 흐름 경계 — 노드가 처리 단계면 여기, 저장소·자산이면 데이터 흐름; 두 질문이 늘 한 발화로 나오면 합침.
- **데이터 흐름·파생 데이터** — 질문: 이 데이터의 원본은 무엇이고, 어떤 단계를 거쳐 어디에 복제되며, 얼마나 늦어도 되나? · 그림: DFD 계열 박스-화살표 — 박스 = 저장소·데이터 자산, 화살표 = 이동, 라벨 = 이동 방식·주기, 외부 엔티티·신뢰 경계 표시. **스키마·필드는 안 그림**(데이터 모델 행 몫) · 필수요소: ① 원본(source of truth) 표시("없음 확인" = 이중 원본, 드러나야 할 값) ② 변환 단계(집계·필터·마스킹 한 단어) ③ 이동 방식(CDC·배치·동기 write-through·폴링·pub/sub) ④ 지연 허용치 — 수치 + 위반 시 동작 ⑤ 저장소와 소비자("없음 확인" = 아무도 안 쓰는 파생 데이터) ⑥ 분류·신뢰 경계 · 라우팅 예외: 처리 속도·실패 재처리 → 큐·배치 / 원본이 이벤트 스토어 → 이벤트 소싱 / 읽기 모델 동기화 → CQRS / 복제 방식·파티션 키 → 저장소 토폴로지 / 계획(단계·롤백) → 마이그레이션 · 02 재판정: 큐·배치 × 데이터 흐름 경계(위 행 참조).
- **마이그레이션** — 질문: 지금 것에서 새 것으로 어떤 단계를 거쳐 옮기고, 각 단계에서 무엇이 어디를 읽고 쓰며, 어디까지 되돌릴 수 있나? · 그림: **단계 수만큼 같은 종류 그림을 나란히**(before/after 두 그림으로 한정하던 규칙 폐기), 각 그림은 그 단계의 읽기·쓰기 경로만, 단계 이름이 frame 제목. 선은 대부분 코드에 없어 근거 태그 `설계` · 필수요소: ① 단계 목록과 현재 단계 ② 단계별 읽기·쓰기 경로(읽기 전환과 쓰기 전환은 다른 단계) ③ 이중 쓰기 구간 ④ 원본 이동 시점 ⑤ 정합성 검증 방법("없음 확인" = 검증 없는 컷오버) ⑥ 롤백 가능 구간과 만료 조건 ⑦ 정리 단계 · 라우팅 예외: 다 끝난 뒤 구조 → 해당 구조 상황 / 배포 단위 교체 → 배치도(배포 롤백 ≠ 데이터 롤백) / 코드 인터페이스 변경만 → API 계약 / 지금 상태(원본·계보) → 데이터 흐름.

*운영*
- **장애 대응 흐름** — 질문: 장애가 감지되면 누가 무엇을 어떤 순서로 하고, 무엇을 보고 끝났다고 하나? · 그림: 스윔레인 플로우 — 역할별 가로 레인 × 단계 진행, 액션 = 사각형, 판단 = 마름모, 담당 없는 단계는 빈 레인으로 드러냄 · 필수요소: ① 감지 신호 ② 분류·심각도와 선언 기준(등급 값은 스킬이 안 정함) ③ 역할 배정(지휘·운영·소통) ④ 완화·롤백 동작 ⑤ 에스컬레이션 경로 ⑥ 복구 확인 기준과 전파 · 라우팅 예외: 이미 난 장애의 시각별 원인 → 장애 원인 분석 / 어디 떠 있나 → 배치도 / 코드가 자동으로 재시도·분기 → 재시도·분기.

- **성능 병목** — 질문: 이 요청의 시간은 구간별로 어디에 얼마나 쓰였고, 전체를 줄이려면 어디를 줄여야 하나? · 그림: 트레이스 워터폴 — 공유 가로 시간축, 구간마다 막대 하나, 부모-자식은 들여쓰기, 겹치면 병렬·이어지면 직렬, 임계 경로 강조. 플레임 그래프는 같은 그림에 안 섞음(시간축 아님) · 필수요소: ① 구간별 소요(계측 없는 구간은 0이 아니라 "확인 못 함") ② 전체 대비 비율 ③ 직렬/병렬 구간(판별 = span 시작·종료 시각의 겹침. child-of/follow-from 관계 타입은 대기·인과 근거로만 쓰고 직렬/병렬 판별에 쓰지 않음 — 동시에 도는 자식 여럿도 child-of일 수 있음. 시각 없으면 "확인 못 함") ④ 임계 경로(합류 지점 확인, 대기·합류 근거 없으면 "확인 못 함") ⑤ 측정 기준 — 백분위수·표본·계측 지점 · 라우팅 예외: 1회 장애의 벽시계 흐름 → 장애 원인 분석 / 처리량·백프레셔 → 큐·배치 파이프라인 / 락 대기 → 동시성·락 / 자원 포화(CPU·커넥션)가 쟁점 → 이 그림 아님(02에서 신호 나오면 재검토).

**2. 캔버스 우선**
- 에이전트는 매 턴 행동 전에 CLI `screenshot`(MCP `get_canvas_screenshot`)으로 캔버스를 본다. 사용자 표시는 모델이 그림과 구분해 읽는다 — 색·모양을 규칙으로 정하지 않는다.
- 사용자가 옮긴 배치 = 정답. 에이전트는 사용자가 옮긴 요소의 좌표를 건드리지 않고, 자신이 새로 그리는 요소만 정렬한다(2026-09-19 A6 — 구 "정렬만 다듬는다"는 03의 좌표 유지 인수 기준과 충돌해 교체). 판별은 CLI `describe`(MCP `describe_scene`)의 요소 좌표 변화.
- 사용자가 준 손그림·사진 = 초안. 정식 그림으로 옮기되 사용자 배치 순서를 유지한다.
- 새 툴을 만들지 않는다. yctimlin의 양방향 캔버스 위에 얹는 행동 규칙 두 줄이 전부다.
- **자가 수정 정지** (2026-09-11 그릴 확정, archify #6 재작성): 같은 문제(라벨 겹침, 근거 못 찾음 등)를 두 번 고쳐도 안 나아지면 그만 고치고 사용자에게 말한다("라벨 겹침 못 잡음, 직접 옮겨달라" / "order→payment 근거 못 찾음, 점선 유지"). 렌더러 거부 루프는 없지만 스크린샷 자가 검사·근거 없음 표시로 에이전트 혼자 도는 루프가 있어서. 횟수 2는 경험칙, 도그푸딩 후 조정.
- **라벨 삭제는 수리 아님** (2026-09-11 그릴 확정, archify #7 재작성): 화살표 라벨 겹침은 옮기기·줄이기로만 고친다. 라벨은 의미(동기/비동기, 프로토콜, 방향)라서 지우면 그림이 거짓이 됨. 예외: 양끝 박스만으로 뜻이 완전히 드러나는 라벨. 필수요소 "항목 삭제 금지"의 화살표 버전.
- **"안 그림" 한 줄** (2026-09-11 그릴 확정, archify #4 receipt 재작성): 그림 밑에 텍스트 한 줄 "안 그림: ___". 같은 레벨인데 일부러 뺀 것만 적는다(예: L3에서 이벤트 구독선 생략). 레벨 규칙으로 빠진 것·근거 등급(점선)은 중복이라 안 적음. 없으면 생략. 캔버스에 넣어 스크린샷·저장에 같이 남긴다. 사용자가 보고 "그것도 그려줘" 하면 같은 종류면 덧그리고, 다른 종류면 옆에 새 그림. 도면 모드에선 범례로 승격.

**3. 줌 레벨 + 근거 추출**
- 그림 선택을 안내하는 레벨 5개, 스택 무관(고정 포함 트리가 아님): L1 시스템 컨텍스트 / L2 배포 단위 / L3 모듈 경계 / L4 레이어 / L5 경계 타입(포트 인터페이스와 구현체). C4의 Context·Container·Component에 모듈 층을 끼운 형태 — Gradle 멀티모듈·Nest 모듈이 C4에 없는 칸이기 때문.
- 확대는 실제 구조를 따르며, 중복 단계 생략과 공용 모듈 그림의 공유 참조를 허용한다. 박스 라벨에 확대할 그림 참조를 남긴다. 공용 모듈의 내부 그림은 하나로 두고 사용하는 배포 단위들이 함께 참조한다. 내부 탐색은 사용자 발화로 요청하며, 에이전트는 캔버스에 해당 내부 그림이 있으면 그 위치로 화면을 이동·확대하고 없으면 새로 그린다(03 담당). 박스 클릭 탐색을 요구하지 않는다. 산출물 경로·파일명은 §3.5를 따른다. 함께 저장한 그림 사이의 참조는 새 캔버스에 불러온 뒤에도 보존되어 같은 내부 그림으로 탐색할 수 있어야 한다. 참조 생성·탐색은 03, 저장·재로드 시 참조 보존은 06 담당이며 그림 구분은 05의 frame을 사용한다.
- 각 레벨에 넣을 디테일 수준 고정: L2에 엔드포인트·토픽명, L3에 모듈명·소유 테이블명(클래스 없음), L4부터 클래스. 상위 그림에 하위 디테일 금지. (2026-09-11 정정: 구 "L3에 클래스명"은 L4·L5와 중복이라 삭제)
- **L4 정의** (2026-09-11 그릴 확정): 모듈 안 레이어. 레이어 이름·칸은 **프로젝트 아키텍처 스타일 그대로** — 헥사고날: adapter-in / application(in-port·service·out-port) / domain / adapter-out. 클린: entities / use-cases / interface-adapters / frameworks. 3티어: controller / service / repository. 스타일은 에이전트가 패키지명·ArchUnit 규칙·모듈 구조에서 판별, 못 읽으면 되물음. 스타일 무관 공통 필수요소: **의존 화살표 + 방향 위반 빨강 표시**(domain→infra 같은 것). 위반이 모듈마다 달라서 레이어 그림이 모듈별로 가치 있음. L5 = 경계(out-port 등)의 타입 확대. 모듈 자체가 레이어이면 별도 L4 그림을 건너뛰고 L3에서 L5로 내려간다.
- **DDD 매핑** (2026-09-11 그릴 확정): 레벨 추가 없음. 전략 — 바운디드 컨텍스트는 배포·모듈과 일대일로 고정하지 않고 실제 코드·설계의 도메인 경계대로 표시한다. 박스 하나와 일치하면 이름을 붙이고, 박스 하나 안에 여러 컨텍스트가 있으면 내부 경계를, 여러 박스에 걸치면 묶는 경계를 표시한다. 컨텍스트 관계(ACL·shared kernel·conformist·upstream/downstream)는 컨텍스트 사이 화살표 라벨이며 배포 단위 간 연결과 동일시하지 않는다. 전술 — L4 domain 칸에 《aggregate》《domain service》《event》 스테레오타입, 애그리거트 내부 엔티티는 안 나열. DDD+헥사고날이면 UI·Infrastructure 자리를 adapter-in·adapter-out이 대체.
- **확대 예시 (2026-09-14 그릴 확정, 검수 R06):** 기능별 모듈은 배포 단위 → 주문 모듈 → 주문 내부 레이어 → 경계 타입으로 내려간다. 레이어별 Gradle 모듈(domain·adapter)은 모듈 그림에 이미 레이어가 드러나므로 별도 레이어 그림 없이 해당 경계 타입으로 내려간다. 주문 API·정산 워커가 공용 인증 모듈을 쓰면 각 배포 단위 그림에 사용 관계를 표시하고 같은 공용 모듈 내부 그림을 참조한다. 단계 생략은 상위 그림에 클래스 디테일을 섞으라는 뜻이 아니며, 각 그림의 허용 디테일은 유지한다. 구현·예시 검증 담당은 03.
- L5는 경계에 있는 타입만(포트와 구현체). 내부 클래스 나열 금지 — 낡는 속도 때문.
- 근거 등급은 세 가지다 — 선언(빌드 파일·모듈 데코레이터) / 관례(디렉터리 구조) / 추론(import 파싱, 점선 표시).
- **근거 검증은 서버, 판단은 에이전트** (2026-09-11 그릴 확정, archify #5 `repository-evidence.mjs` 재작성): 선·값마다 근거 태그 `코드` / `설계` / `로그` 중 하나. `코드` 태그는 `파일:줄`을 함께 적고, **그릴 때마다** 서버가 그 파일·줄 존재를 확인한다 — 파일이 없거나 지정한 줄이 파일 범위 밖이면 점선으로 강등 + 캔버스에 "근거 없음: order→payment" 표시. 의미(정말 의존성인지)는 검사 안 함. `설계`(합의됐거나 논의 중인 계획·계약 — 마이그레이션 계획, API 계약 협의, 변경안처럼 코드에 아직 없는 선) · `로그`(장애 타임라인)는 검사 없음, 기록만. 근거 태그는 캔버스에 보이지 않는 요소 데이터다 — 서버(검사)와 에이전트(`describe`)만 읽고, 사용자는 점선과 `추론`·`근거 없음` 라벨을 본다(2026-09-12 그릴 확정). 저장 시점이 아니라 매번 검사하는 이유: 틀린 그림으로 대화하면 저장 전에 이미 손해.
- **근거 추출 = 원칙 3줄, 스택 표 없음** (2026-09-11 그릴 확정, 구 "첫 스택 하나"·"스택별 어댑터 테이블" 폐기): ① 의존이 선언된 파일을 먼저 찾아라(빌드 파일·모듈 데코레이터) ② 없으면 디렉터리 관례 ③ 그래도 없으면 import 추론, 점선. **선언 파일·관례가 증명하는 것은 "의존한다"까지다** — 실제로 부른다·구독한다·실패를 처리한다는 관계는 해당 호출·구독·처리 코드 줄이 근거일 때만 실선이고, 의존 선언만 있으면 `추론` 점선(2026-09-19 2차 검수 A3). 스택별 파일명(`build.gradle`, `pom.xml`, `@Module`, `go.mod`…)은 모델이 이미 알아서 표로 안 적음 — "Claude가 아는 건 빼기" 규칙. 아키텍처 스타일 판별(헥사고날·클린·3티어)도 같은 원칙(패키지명·ArchUnit → 관례 → 되묻기). 서버는 근거의 파일·줄 존재만 확인한다. 그림의 선·값이 그 내용과 맞는지는 에이전트가 판단한다. 도그푸딩에서 특정 스택의 선언 파일을 모델이 반복해서 못 읽으면 그 스택만 서버 파서(결정론)로 승격. 주력 검증 스택: Spring Java/Kotlin(Gradle·Maven), NestJS.
- **같은 레벨 과밀 처리** (2026-09-11 그릴 확정, archify #3 재작성): 한 그림에 주노드가 대략 10~15를 넘으면 그 레벨 안에서 코드 경계(패키지·디렉터리·팀)로 한 겹 묶어 **개요 그림 + 묶음별 그림**으로 나눠 그린다. 전부 같은 캔버스, 다른 영역 — 기존 그림은 건드리지 않는다. 숫자는 지침이지 규칙 아님(판단은 에이전트, 자동 검사는 "묶였는가"만). 도면 모드는 예외. 용어: **그림 = 캔버스 위 독립 영역 하나**, "한 그림에 한 종류"는 그림 단위.

**선 표기** (2026-09-14 그릴 확정, 검수 R05)

점선은 확인되지 않은 선·값 전용이다. 통신 방식과 근거 상태는 독립적으로 읽는다.

| 상황 | 선·화살촉 | 보이는 라벨 |
|---|---|---|
| 확인된 동기 호출 | 실선 + 채운 화살촉 | 호출 이름 + `[동기]` |
| 확인된 비동기 이벤트 | 실선 + 열린 화살촉 | 이벤트 이름 + `[비동기]` |
| 확인된 응답 | 실선 + 열린 화살촉 | `응답: 결과` |
| 추론한 관계 | 점선 | 관계 이름 + `추론` |
| 코드 근거 검사 실패 | 점선 | 관계 이름 + `근거 없음: A→B` |

- 점선으로 바뀌어도 화살촉과 통신 방식·응답 라벨은 유지한다. 통신 방식을 확인 못 했으면 `[동기]`·`[비동기]`를 추측해 붙이지 않는다. 필수요소의 "확인 못 함" 표시는 유지한다.
- 그림마다 사용한 표기의 범례를 넣는다. `설계` 선의 실선 + 새 색 규칙은 유지한다.
- 응답을 실선으로 그리는 것은 archdraw의 표기 선택이다. 기존 조사에서 확인한 UML 응답 점선과 다르며, 점선을 불확실성 전용으로 남기기 위한 결정이다([기존 조사 §4-3](research-request.md)).
- 03은 스킬·조작 가이드에 이 규칙을 반영하고, 07은 서버 강등·복구 때 통신 표기를 보존한다.

**3.5 캔버스는 지우지 않는다 (2026-09-11 3차 그릴 확정 — 구 "자동 보관" 폐기)**
- 에이전트는 캔버스를 지우거나 덮지 않는다. 새 그림은 **새 frame**(7-6)을 옆에 그린다. `clear`는 사용자 발화("지워")로만. 그래서 "아까 그 그림"은 캔버스에 그대로 있음.
- 구 §3.5 "clear·덮기 직전 서버가 scratch/에 자동 export"는 삭제. 이유: 출처 없는 우리 발명이었고, 위 규칙이면 지워지는 순간 자체가 없음. 남는 유실은 서버 크래시·재부팅 때 저장 안 한 그림뿐 — "기본 안 남김" 원칙상 버릴 그림. 세션 종료 감지 문제(구 Next Steps 2)도 같이 소멸.
- 데이터 폴더: `$CLAUDE_PLUGIN_DATA/`(Codex `$PLUGIN_DATA`, 둘 다 없으면 `~/.excalidraw-architect/`) 아래 `snapshots/<프로젝트 식별자>/`(7-2) + `tmp/`(7-5c 스크린샷 png). `scratch/` 없음.
- **프로젝트 루트·저장소 범위 (2026-09-14 그릴 확정, 검수 R03):** `session start`가 cwd에서 git 루트를 찾아 세션의 프로젝트 루트로 고정한다(없으면 cwd, `--project <경로>`로 덮어쓰기, 출력에 잡힌 루트 표시). 이후 호출은 `--session` 키만으로 같은 프로젝트를 가리켜 하위 폴더·스킬 폴더에서 불러도 근거 검사(7-3)와 스냅샷의 프로젝트 구분이 그 루트 기준이다. 산출물 export 경로는 별도로 지정하며 고정하지 않는다(2026-09-16). 스냅샷은 프로젝트별 하위 폴더(식별자 = 루트 경로 해시)에 두고, 같은 프로젝트의 세션들과 다음 날 새 세션이 공유한다 — 캔버스는 세션별(7-8), 스냅샷은 프로젝트별. 같은 이름 저장은 `snapshot save`·`export` 모두 기본 거부(있음·만든 시각 출력), `--force`로만 덮어쓴다 — §3.5 "안 지움"을 파일에도 적용. 기각: 매 호출 cwd(하위 폴더 호출 시 어긋남) / `--project` 매번(인자 증가) / 세션별 스냅샷 폴더(세션 키가 사라져 다음 날 못 찾음, 스토리 17 위반) / 조용한 덮어쓰기·자동 접미사. 담당: 루트 고정은 04, 저장소 범위·동명 정책은 06.
- **저장 범위·파일 단위 (2026-09-14 확정, 2026-09-16 경로·파일명 수정, 검수 R07):** "저장해"는 캔버스 전체를 현재 그림들의 배치와 함께 `.excalidraw` 파일 하나로 저장한다. "주문 그림만 저장해"처럼 대상을 지정하면 그 그림만 저장한다. 범위는 매번 되묻지 않고, 지정 대상이 애매할 때만 확인한다. 산출물 저장 경로는 고정하지 않는다. 사용자가 지정한 경로·파일명은 그대로 따르고, 경로가 없으면 에이전트가 프로젝트의 기존 문서 배치를 보고 저장 폴더를 선택한다. 파일명을 지정하지 않으면 에이전트가 그림 내용을 보고 영어 파일명을 정해 별도 경로·이름 확인 없이 저장하고, 성공 후 파일명을 포함한 저장 경로를 알려준다. 기존 동명 파일 거부 규칙은 유지한다. 발화 해석·경로와 이름 결정·결과 안내는 03, 전체·선택 export와 배치 보존은 06 담당. 스냅샷 이름은 아래 자동 이름 규칙을 따른다.
- **스냅샷 보존·안내 (2026-09-16 합의, 검수 R07):** 스냅샷은 디스크에 보관하며 TTL 없이 유지한다(06 담당). 생성 성공 후 서버 종료·재시작 뒤에도 남고 자동 만료되지 않는다고 알린다(03 담당). 업스트림의 메모리 스냅샷은 교체 대상이며 제품의 보존 정책이 아니다.
- **스냅샷 자동 이름 (2026-09-16 합의, 검수 R07):** 이름을 생략하면 에이전트가 캔버스 내용을 나타내는 영어 이름(확장자 제외)을 정하고, 스냅샷 생성 시각을 UTC 초 단위로 앞에 붙여 `YYYY-MM-DD_HHmmssZ_<영어 이름>`을 사용한다(예: `2026-09-16_053012Z_order-flow`). 직접 지정한 이름은 그대로 쓴다. 같은 초에 같은 이름이 생기면 기존 동명 거부 규칙을 적용하고 충돌을 알린다. 자동 접미사나 덮어쓰기는 하지 않는다. 03은 이름 결정·안내, 06은 이름을 받는 저장 경로·동명 거부를 담당한다.
- **필수요소 규칙**: 상황별 필수요소는 그림에 항상 값이 있어야 한다 — 코드에서 읽은 실제 값 / 없음이 확인됨 / 확인 못 함(점선). 항목 삭제 금지. "저장해" 시점에 "확인 못 함"이 남아 있어도 점선과 해당 표시를 유지해 바로 저장하고, 미확인 항목을 사용자에게 알린다. 값을 채우거나 추가 확인을 받을 때까지 저장을 막지 않는다. 안내는 03, 저장·재로드 시 표시 보존은 06 담당이다. 그 외 시점엔 검사 없음.

**3.7 포크 범위 — 서버 작업 목록** (2026-09-11 그릴 확정, 항목별 기존/추가 표시)
- 사실(조사): CLI 이미 있음(`dist/bin.js`, 18 서브커맨드 — 스펙의 `server/bin/cli.js` 표기는 오기) / 요소·스냅샷 전부 메모리 Map(`src/types.ts:288-300`), 디스크 영속화 없음(README 423·552·577줄 명시) / export는 `EXCALIDRAW_EXPORT_DIR` 한 폴더 밖 쓰기 거부 / 요소 종류에 `frame` 없음(`frameId` 칸만) / 캔버스 서버는 머신당 하나(포트 3000, pid 파일) — 세션 구분 없음 / 캔버스 = `@excalidraw/excalidraw` 0.18.1(MIT), yctimlin MIT.
- **7-1 자동 보관 [삭제, 3차]**: §3.5 참조. 서버 작업 없음. 대신 스킬 규칙 한 줄(캔버스 안 지움, 새 frame).

  - **그림 단위 저장·복사 (2026-09-14 그릴 확정, 검수 R02):** 캔버스에 그림이 여러 개이므로 저장·복사·복원 단위를 나눈다. `export`는 기본 전체, `--frame <이름>`이면 그 그림만. `import`는 지우지 않고 얹으며 요소·frame·바인딩 ID를 한 세트로 항상 새로 발급해 독립 복사본을 만든다(`--replace` 삭제). 캔버스를 지우는 명령은 `snapshot restore` 하나. 복사본은 현재 내용 오른쪽에 `"<원본> (복사)"` 이름으로 놓는다. 이유: 업스트림은 캔버스 하나 = 그림 하나라 전체 단위로 충분했지만, §3.5(캔버스 안 지움) + 스토리 17(before/after 나란히)에서는 전체 복원이 다른 그림을 지우고 ID 보존 merge가 원본을 덮어썼다. 기각: 요소 ID 목록 지정(그림 경계 표현이 frame과 이중), 사용자 수동 복붙(에이전트가 스토리 17을 못 함), `--mode replace|merge` 통합(지우는지가 옵션 값에 숨음). 담당 06.
- **7-3 근거 검사 [추가]**: 요소에 `evidence: {tag: code|design|log, path, line}` 칸. 생성 경로(`mcp-dispatch` create/batch, CLI `add`) 공통 함수에 검사 삽입 — `code`면 파일·줄 존재 확인, 없으면 점선 강등 + "근거 없음: A→B" 텍스트 자동 생성. 모양은 archify `repository-evidence.mjs`, 거부 대신 강등·태그 3종은 우리 판단. 레포 위치 = 세션의 프로젝트 루트(§3.5, 검수 R03). **생성 후 수명주기 (2026-09-14 그릴 확정, 검수 R04):** 근거 칸이 바뀌면 생성·수정·import·restore 어디서든 같은 검사(검사 통과 = 현재 프로젝트의 파일·줄 존재 확인. 의존성의 의미는 보장하지 않는다). 서버가 내린 선은 근거가 맞아지면 서버가 올린다("서버 강등" 표시로 추론 점선과 구분 — ADR-0005 "내리기만"을 좁힘). ## Testing Decisions

- 시임은 하나: **스킬 호출.** 입력 = 사용자 발화 + (선택) 레포 + (선택) 캔버스 상태. 출력 = 어떤 그림을 어떤 레벨로 그렸는가. 내부 판단 과정은 검사하지 않는다.
- 좋은 테스트 = "이 발화에 이 종류의 그림이 나오는가", "이 레벨 그림에 금지된 디테일이 없는가", "사용자가 옮긴 요소의 좌표가 유지되는가". CLI `describe`는 요소·라벨·연결을 파악하는 데 쓴다. 출력이 있다는 사실만으로 그림 종류나 내용이 맞다고 판정하지 않는다. 좌표 유지 여부는 반올림된 `describe` 출력 대신 실제 요소 데이터를 전후 비교한다.
- 가독성은 기존 스킬처럼 `screenshot`(`get_canvas_screenshot`)으로 받은 이미지를 에이전트가 보고 확인한다. 글자 잘림·도형 겹침·화살표와 도형 및 라벨의 겹침을 확인하고 문제가 있으면 수정 후 다시 찍는다. 자가 수정은 기존 두 번 실패 시 중단 규칙을 따른다. 캔버스가 열린 브라우저 탭은 필요하지만 별도 브라우저 조작 도구를 추가하는 요구는 아니다.
- ~~라우팅 테이블 트리거 eval~~ → 수동 스킬이라 트리거 eval·description 최적화 없음. 대신 skill-creator의 with/without 비교 eval(발화 → 기대 그림 종류·레벨·필수요소)만.
- 구현 인수 확인은 각 이슈에서 수행한다. 02 도그푸딩 뒤 03의 후속 작업으로 with/without 비교 eval을 수행한다. 같은 발화·근거·초기 캔버스에서 스킬 사용 여부만 달리하고, 미리 정한 그림 종류·레벨·필수요소와 대조한 의미 평가 및 스크린샷 확인 결과를 별도로 기록한다. 규칙의 유지·수정·제거는 기존처럼 사용자가 도그푸딩 기록을 보고 판단한다.
- 검증 책임과 관측 수단은 03(스킬 판단·대화·탐색), 05(frame·글꼴·브라우저 동작), 06(저장·재로드), 02(실사용 관찰)의 인수 기준에 둔다. 각 결과는 기대 결과·실제 결과·통과/실패/미시험과 근거를 남긴다. 03의 저장 후 탐색 통합 확인은 06 구현 뒤 수행한다.
