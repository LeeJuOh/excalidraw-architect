# 03: `archdraw` 판단 스킬 본문 — 라우팅 표, 줌 레벨, 캔버스 우선

> 확정된 라우팅 21행(review.md "행 확정 기록" → PRD 반영본)을 그대로 구현한다. 02 도그푸딩은 구현 뒤에 돌리며, 그 판정(`dogfooding-00.md`)이 이 이슈의 수정 사항으로 돌아온다.

**What to build:** 사용자가 `/archdraw 이 API 부르면 뭐가 일어나?`라고 하면 시퀀스 그림이 나오고, `/archdraw 구조가 어떻게 돼?`라고 하면 줌 레벨 그림이 나온다. 에이전트는 매 턴 행동 전에 캔버스를 보고, 사용자가 옮긴 배치는 정답으로 받고, 새 그림은 캔버스를 지우지 않고 옆에 그린다. 업스트림 `excalidraw-skill`은 삭제되고 조작법은 `archdraw`의 references로 옮겨진다.

- 스킬 본문 500줄 이하, 영어. Claude·Codex 공통 본문 하나를 유지하며, 01의 호스트별 호출 정책 파일과 사용 안내를 유지한다(스펙 "수동 스킬", 검수 R11). 상세는 references 3단계(조작법 / 라우팅 표 / 줌 레벨).
- 라우팅 표: 스펙 §1의 21행을 그대로. 행마다 **답하는 질문 한 문장** + 그림 종류 + 필수요소 + 라우팅 예외 + 그리는 규칙. 에이전트는 사용자 발화를 질문 중 하나로 읽고, 사용자가 부른 그림 이름보다 질문을 우선한다 — 사용자는 그림 종류를 모르거나 잘못 알 수 있다고 전제한다. 고른 이유는 채팅에 한 줄, 그림 제목(frame 이름)은 답하는 질문. 두 갈래로 읽힐 때만 되묻고, 되물을 땐 후보마다 아스키 미리보기. 개념 용어(Event Notification 등)는 원어 유지. API 계약 행은 표준 표기가 없는 근사형이라 스킬 문서에도 그렇게 적는다.
- 대화 중 사용(스펙 "대화 중 사용"·"변경안 표기", 2026-09-19 프레임 정리): 세 진입은 같은 동작이고 대상만 다르다. 정방향(에이전트 설명 → 그림, show-me류 요청과 같되 출력은 캔버스)·목적 질문(결정하려고 지금 상태 → §1 상황 그림)·역방향(`네가 이해한 대로 그려봐` = 구현 위임 전 이해 대조 → 코드에서 읽은 지금 구조 + 사람 말의 바꿀 것을 한 그림에, 변경안 표기 → 사용자 편집은 교정·제안·결정 중 하나다. 뜻이 분명하면 그대로 따르고, 분명하지 않으면 묻는다. 코드에 없는 내용은 사실로 받지 않는다. 언제 묻고 어떻게 표시할지는 절차로 적지 않고 모델에 맡긴다 — 2차 검수 A2). 한 번 부른 뒤 같은 대화에서 연결·순서가 들어간 답은 재호출 없이 그림 먼저. 이 동작을 공통 본문에 적고, 실제 후속 턴 적용과 압축 후 재호출·재개는 02 도그푸딩에서 확인한다(호스트의 영구 유지 보장으로 설명하지 않음). 변경안은 지금 구조 위에 바뀌는 부분만 새 색, 코드에 없는 선은 `설계` 태그 실선. "텍스트로 답해" 끄기 규칙은 적지 않는다(02에서 확인). 경계: 구조·흐름·경계는 캔버스, 코드·쿼리·값·이유는 텍스트. L5 아래는 그리지 않는다.
- 태그 붙이는 규칙 한 절(07에서 이관, 2026-09-20): 그리는 선·값마다 근거 태그 `코드`(파일:줄)·`설계`·`로그` 중 하나를 `evidence` 칸에 적는다. 코드에 아직 없는 선(변경안·마이그레이션 계획·협의 중 계약)은 `설계` 태그, 실선 + 새 색 — `코드` 태그로 그리면 07 검사에서 선마다 "근거 없음"이 쌓인다. 파일:줄 존재 검사·점선 강등은 07 서버 몫이며 스킬은 태그를 붙이기만 한다.
- 고정 포함 트리가 아닌 줌 레벨 5개 안내와 레벨별 허용 디테일 ([ADR-0004](../../../docs/adr/0004-five-zoom-levels.md)). 사용자에겐 번호 대신 이름("모듈 경계 그림")으로 말한다. 근거 추출은 원칙 3줄(선언 파일 → 디렉터리 관례 → import 추론은 점선), 스택 표 없음. 선언 파일은 "의존한다"의 근거이며, "부른다·구독한다"는 호출·구독 코드 줄이 있어야 실선(2차 검수 A3).
- 내부 탐색·저장 발화(검수 R07 일부): PRD §3의 내부 탐색과 §3.5 저장 범위·파일 단위를 따른다. 기존 내부 그림으로 화면을 이동·확대하거나 없으면 그린다. 저장 범위는 기본 전체, 명시한 경우 지정 그림이며 대상이 애매할 때만 묻는다.
- 산출물 경로·이름(2026-09-16): 저장 경로를 고정하지 않는다. 사용자가 지정한 경로·파일명은 그대로 따른다. 경로가 없으면 프로젝트의 기존 문서 배치를 보고 저장 폴더를 선택하고, 파일명이 없으면 그림 내용을 보고 영어 파일명을 정한다. 별도 경로·이름 확인 없이 저장하고, 성공 후 파일명을 포함한 전체 경로를 알려준다. 같은 경로에 파일이 있으면 자동 덮어쓰지 않고 06의 동명 파일 거부 결과를 알린다.
- 스냅샷은 06에서 디스크에 보관하며 TTL이 없다. 생성 성공 후 서버 종료·재시작 뒤에도 남고 자동 만료되지 않는다고 안내한다. 업스트림 메모리 방식의 유실 안내는 제품 규칙에 넣지 않는다.
- 스냅샷 이름을 생략하면 캔버스 내용을 나타내는 영어 이름(확장자 제외)을 정하고, 생성 시각을 UTC 초 단위로 앞에 붙여 `YYYY-MM-DD_HHmmssZ_<영어 이름>`으로 만든다(예: `2026-09-16_053012Z_order-flow`). 직접 지정한 이름은 그대로 사용한다. 생성 결과에 실제 이름과 전체 경로를 알린다. 같은 초·이름이 겹치면 06의 동명 거부 결과를 알린다.
- 미확인 필수요소가 있어도 "확인 못 함" 표시와 점선을 유지해 바로 저장하고, 미확인 항목을 사용자에게 알린다. 값 보완이나 추가 확인을 저장 전제조건으로 삼지 않는다.
- 그림 참조를 생성하고 탐색할 때 05의 frame으로 대상 그림을 구분한다. 참조는 박스 요소의 `link` 칸에 `?element=<대상 frame id>`로 적고(ADR-0008), 탐색할 때는 그 값을 읽어 대상 frame을 찾는다. 06이 저장·재로드한 참조를 읽어 기존 내부 그림으로 이동·확대하며, 함께 불러온 공용 내부 그림을 중복 생성하지 않는다.
- 관통 규칙: 한 그림에 한 종류 / 진짜 이름 / 기본은 안 남김. 승격은 사용자 발화로만.
- **저장 상태 표시 (PRD §3.5, 2026-09-19):** 그림으로 답한 턴 끝에 `screenshot` 결과에 동봉된 그림별 저장 상태(저장 경로 / 저장 후 수정됨 / 파일 없음 / 미저장, 마지막 스냅샷)를 채팅 한 줄로 옮겨 적는다. 세거나 기억하지 않는다 — 값은 06 서버가 준다. 저장할지는 묻지 않는다. 사용자가 세션을 끝내자고 하면 미저장·저장 후 수정된 그림이 있을 때 1회만 저장할지 묻고 `session end`를 부른다. 그림마다·호출마다 묻는 지시는 넣지 않는다.
- 캔버스 우선: 턴 시작 `screenshot`, 사용자 표시는 교정·제안·결정 중 하나로 읽고 뜻이 분명하지 않으면 묻는다(삭제·의문 표시를 규칙으로 못 박지 않음), 자가 수정은 두 번 실패하면 멈추고 사용자에게 말함, 라벨 삭제는 수리 아님, 그림 밑 "안 그림" 줄. 초안 시작(스펙 "대화 중 사용", 스토리 33): 초안은 옆에 정식으로 옮기고 원본은 두며, 박스마다 `코드`/`설계` 태그로 가르고, 이후 턴은 박스 단위로 내부 그림을 참조로 채운다.
- 과밀: 주노드 10~15 넘으면 개요 그림 + 묶음별 그림.
- 조작법(커맨드 호출 순서)은 업스트림 스킬에서 `references/canvas-ops.md`로 옮긴다. `install-skill` 커맨드는 삭제한다(플러그인 `skills/` 자동 로드).
- 규격 단일 원본([ADR-0006](../../../docs/adr/0006-canvas-guide-single-source-via-mcp.md), 서버 몫은 09): SKILL.md·`references/canvas-ops.md`는 치수·색·바인딩 값을 적지 않는다. "그리기 전 리소스 `guide://canvas`를 읽는다" 한 줄로 서버 리소스를 가리킨다. 조작법(커맨드 호출 순서)만 `canvas-ops.md`에 남긴다.
- 선 표기(검수 R05): PRD §3 "선 표기"의 결정을 스킬과 조작 가이드에 적용한다. 라벨 문자열은 `docs/canvas-guide.md` 선 표기 표가 원본이며 영어 고정이라([ADR-0012](../../../docs/adr/0012-canvas-labels-fixed-english.md)) 스킬 문서에 다시 적지 않고 `guide://canvas`를 읽어 쓴다. 추론 점선에는 추론 표시, 각 그림에는 사용한 표기의 범례를 넣는다. 서버 규격 md의 선 표기 교체는 09가 한다. 응답 실선은 의도적인 UML 표기 차이로 적는다. 서버 강등·복구의 통신 표기 보존은 07 담당.

## 검증 방법과 결과 기록 (R10)

구현 담당 에이전트가 아래 방식으로 위 인수 기준을 확인한다. 항목별 기대 결과는 각 체크박스를 따르며, 결과에는 발화·초기 조건·기대 결과·실제 결과·통과/실패/미시험·근거를 남긴다. 의미 평가와 화면 확인은 별도 결과로 적는다. 보기 좋은 그림도 내용이 틀리면 의미 평가 실패다.

### 통한 것

- 문서 인수를 스크립트로 먼저 쓰고(빨강) 본문을 채운 순서. 삭제 인수까지 스크립트가 잡아줬다.
- `/code-review` 2축 병렬. 스크립트가 통과하는데 내용이 틀린 것 3종을 전부 거기서 잡았다 — 스펙 §4 모드·이식 원칙 2개 누락, ADR-0006 위반 2곳, SKILL.md §2가 MCP 경로에 요소 포맷을 막던 구조 오류.

### 안 통한 것

- ⚠️ **자동 검사로 본문 누락은 못 잡는다.** `check-skill-docs.mjs`는 줄 수·행 수·리터럴 부재만 본다. 스펙 대조는 읽어야 한다.
- ⚠️ **규격 복사를 조심할 것.** `canvas-ops.md`가 "규격은 `guide://canvas`에 있다"고 적고 바로 아래에서 가이드 문장 2개와 노드 크기를 다시 적고 있었다. 정규식에 JSON 크기를 추가했지만 산문으로 쓴 치수는 여전히 못 잡는다.
