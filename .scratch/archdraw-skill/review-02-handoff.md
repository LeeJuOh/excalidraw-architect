- 원래 요청은 검수만이었다. 이번 승인은 신규 인계 문서 작성까지다. 다음 세션에서도 검수 후보를 곧바로 제품 문서 수정이나 구현으로 옮기지 않는다.

## 반드시 이어받을 사용자 정정

에이전트가 ‘그림은 저장하지만 합의·선택 이유·미결을 구현에 넘기는 책임이 불분명하며 가장 큰 공백’이라고 보고했으나, 사용자는 **의도와 선택 이유는 문서나 ADR이 맡으면 되는 것 아닌가**라고 지적했다. 에이전트는 범위를 넓혀 판단했음을 인정했다.

현재 정리: archdraw는 그림으로 설명하고 사용자 교정을 반영한다. 개발을 수행하는 에이전트가 기존 프로젝트 문서화 규약에 따라 중요한 선택 이유와 합의를 PRD·이슈·ADR 등에 기록하고 구현에 활용한다. 그림은 그 문서에서 참조할 수 있는 보조 자료다.

**별도 인계 시스템, 그림 안 결정 기록 기능, 자동 ADR 생성은 필수 기능 누락으로 제안하지 않는다.** 이 항목은 구현 차단 문제에서 제외하고, 필요하면 책임 범위를 짧게 명확히 하는 선택적 문서 개선으로만 검토한다. archdraw 자체의 ADR과 사용 대상 프로젝트에서 내리는 설계 결정의 ADR도 구분한다.

## 다음 세션 진행

1. 이 문서와 1차 검수의 최신 완료 상태, 작업 트리를 확인한다. 완료 조건: 기존 해결 사항과 이번 후보가 구분된다.
2. 첫 후보는 아래 A1(성능 병목의 직렬·병렬 판별 오류)을 권장한다. ‘어떤 문제인지 → 실무 반례 하나 → 현재 규칙 → 최소 수정안’만 짧게 설명한다. 사용자는 상세 목록을 한꺼번에 듣기보다 큰 그림부터, 이후 하나씩 보는 것을 원한다.
3. 각 후보의 현재 근거를 다시 확인하고 사실·설계 판단·실사용 가설을 구분한다. 완료 조건: 반영·기각·보류와 이유가 정해진다. 순서는 사용자의 선택에 따른다.
4. 사용자가 반영을 요청하면 해당 범위만 수정하고 이 문서에 처리 결과를 남긴다. 기존 1차 검수의 완료 기록을 새 후보의 상태표로 재사용하지 않는다.

원래 요청한 최종 결과 형식은 **구현 전 해결할 문제 / 도그푸딩에서 확인할 가설 / 선택적 개선**이며, 항목마다 근거 위치·실제 실패 예시·최소 수정안을 요구했다. 아래는 그 결과를 확정하기 위한 인계 재료다.

## A. 구현 전 확인·수정 후보

### A1. 성능 병목의 직렬·병렬 판별 — 원문으로 확인한 오류

- 근거: [PRD](spec.md) 라우팅 ‘성능 병목’의 `child-of = 직렬 / follow-from = 병렬`, [기존 조사](research-operations.md)의 후보 ③. [OpenTracing specification](https://opentracing.io/specification/) ‘References between Spans’는 동시에 실행되는 여러 child도 ChildOf일 수 있으며 FollowsFrom도 시간상 겹침을 보장하지 않는다고 예시한다.
- 반례: 부모가 두 RPC를 동시에 호출하고 둘 다 기다리는 fan-out을 직렬로 그려 총시간과 개선 지점을 잘못 판단한다.
- 최소 수정 후보: 관계 타입은 인과·결과 의존의 근거로, 시간 겹침은 시작·종료 시각으로 판단한다. 임계 경로는 대기·합류 관계도 확인하고 근거가 부족하면 미확인으로 남긴다. 03에 병렬 child 반례 하나를 인수 확인으로 추가하는 정도다.

### A2. 사용자 교정의 의미 처리 — 설계 판단 후보

- 근거: [PRD](spec.md) 스토리 7·8·30 및 ‘캔버스 우선’, [03](issues/03-archdraw-skill-body.md)의 교정 규칙과 좌표 유지 인수 기준, [CONTEXT](../../CONTEXT.md)의 ‘사용자 표시’. 배치 보존은 명확하지만 수정 의도 판별과 처리한 표시 정리의 확인 기준은 상대적으로 약하다.
- 반례: 사용자가 화살표를 바꾼 것이 ‘현재 코드 설명이 틀렸다’는 교정인지 ‘앞으로 이렇게 바꾸자’는 변경안인지 구분하지 않고, 코드 사실로 받아들인다. 원을 그려 의문을 표시했는데 삭제 지시로 해석할 수도 있다.
- 최소 수정 후보: 명확한 교정은 바로 반영하되 의미가 갈리는 부분만 짧게 되묻는다. 코드 설명 교정과 변경안을 구분하고, 의도를 반영한 뒤 처리된 표시를 정리하는 사례를 03에서 확인한다. 모든 편집에 승인 절차를 붙이거나 그림에 합의 관리 기능을 만드는 제안은 아니다.

### A3. 근거 추출 규칙의 적용 범위 — 설계 판단 후보

- 근거: [PRD](spec.md) §3의 선언 파일 → 디렉터리 관례 → import 추론, [CONTEXT](../../CONTEXT.md)의 근거 등급, [ADR 0005](../../docs/adr/0005-server-checks-evidence-and-demotes.md). 파일·줄 존재만 검사한다는 서버 보장 범위는 1차 E03에서 이미 해결됐으므로 재지적하지 않는다.
- 반례: 빌드 의존 선언을 실제 API 호출이나 이벤트 구독의 근거로 그대로 사용한다. 파일·줄은 존재하므로 실선이지만 런타임 관계는 확인하지 못했다.
- 최소 수정 후보: 선언 우선 규칙이 증명하는 관계의 범위를 좁혀 적는다. 런타임 순서·실패 처리·운영 수치는 해당 코드·설정·관측을 별도로 확인하고 없으면 미확인으로 표시한다. 서버에 의미 분석기를 만드는 요구가 아니다.

### A4. 브라우저 동기화와 근거·경고 수명주기 — 코드 경로 확인, 계약 보완 후보

- 근거: [07](issues/07-evidence-check.md) ‘생성 후 수명주기’, [ADR 0005](../../docs/adr/0005-server-checks-evidence-and-demotes.md)의 모든 유입 경로 요구. 실제 [server.ts](../../src/server.ts)의 `POST /api/elements/sync`는 메모리 요소를 전체 교체하며, [App.tsx](../../frontend/src/App.tsx)의 `syncToBackend`가 이 경로를 쓴다. 이슈는 PUT·CLI·MCP·import·restore를 열거하고 브라우저 메타데이터 보존을 확인하지만, sync의 경고 정합성 검증은 구체적이지 않다.
- 반례: 브라우저에서 강등된 선을 지웠을 때 부속 경고가 남거나, 근거와 관계가 바뀐 편집이 기존 검사 경로를 우회한다.
- 최소 수정 후보: 07의 공통 검사·부속 경고 정리 경로에 frontend sync를 명시하고 브라우저 삭제·수정 사례를 확인한다. ‘모든 경로’ 요구가 이미 있으므로 새 기능 누락인지 구현 체크 보완인지 구분해 판정한다. 실제 재현은 아직 안 했다.

### A5. 일부 그림만 저장할 때 외부 참조 — 미정 계약 후보

- 근거: [03](issues/03-archdraw-skill-body.md)의 그림 참조·탐색, [06](issues/06-snapshot-and-export-persistence.md)의 `export --frame` 및 ID 재매핑. 함께 저장한 A→B는 보존 요구가 있으나 A만 저장할 때 포함되지 않은 B를 어떻게 다룰지는 명확하지 않다.
- 반례: A만 불러온 뒤 ‘내부 보여줘’가 이전 캔버스의 B 또는 이름이 같은 다른 B를 가리킨다. 복사본 이름이 반복될 때 이름 기반 선택도 모호해질 수 있다.
- 최소 수정 후보: 파일 밖 대상은 미포함 참조로 남기고 기존 대상이 있다고 오인하지 않도록 한다. 참조는 이름 변경·복사에 견디는 식별 방법을 구현에서 정하고, 일부 export와 동일 이름 사례를 06에서 확인한다. B를 자동으로 함께 저장해 사용자 지정 범위를 넓히는 것은 현재 계약과 다르다.

### A6. 남아 있는 문서 계약 불일치 — 정리 후보

- [04](issues/04-session-per-canvas.md)의 프로젝트 루트 설명에 `export 허용 폴더`가 남아 있다. [06](issues/06-snapshot-and-export-persistence.md)·PRD·ADR 0003의 지정 경로 export 정책을 구현자가 되돌릴 수 있으므로 표현 정리 후보다.
- [04](issues/04-session-per-canvas.md)의 `--session` 생략 동작은 ‘착수 전 확인할 제안’이면서 인수 기준이기도 하다. 채택 여부를 구분해야 한다. 06·07은 04의 프로젝트 루트를 사용하지만 착수 의존성에는 04가 없다. 순환 의존이라고 단정하지 말고, 구현 착수와 통합 확인 의존성의 구분이 충분한지 확인한다.
- [PRD](spec.md)의 ‘사용자가 옮긴 배치 = 정답, 정렬만 다듬는다’와 [03](issues/03-archdraw-skill-body.md)의 정확한 좌표 유지가 충돌할 수 있다. 사용자 이동 요소를 정렬 대상으로 삼는지 최소한 명확히 한다.

## C. 선택적 개선과 참고 원문

- **문서화 책임 명확화:** 위 사용자 정정이 우선이다. arc42 9장은 중요한 결정과 선택 이유를 기록하는 책임을 설명한다. [공식 원문](https://docs.arc42.org/section-9/). 전체 arc42 템플릿 도입은 현재 범위 밖이다.
- **C4 차용 설명 정밀화:** [C4 component](https://c4model.com/abstractions/component)는 인터페이스 뒤의 관련 기능 묶음이며 모듈로 표현할 수도 있다. PRD의 ‘모듈이 C4에 없는 칸’이라는 설명은 우리 L3를 별도 안내로 둔 이유와 구분해 다듬을 여지가 있다. [공식 diagrams](https://c4model.com/diagrams)는 유용한 레벨만 사용해도 된다고 설명한다. 우리 5단계를 C4가 보증하는 체계로 표현하지 않는다.

## Suggested skills

- `grilling`: 사용자가 항목을 함께 결정하거나 선택지를 검토하자고 할 때. 한 번에 한 쟁점만 설명하며 확정된 1차 결정을 반복 질문하지 않는다.
- `domain-modeling`: 합의 후 CONTEXT·ADR의 의미나 책임 경계를 수정할 때.
- `writing-for-agents`: 합의한 규칙을 스킬용 명세나 에이전트 인계 문서로 반영할 때.
- `show-me`: 사용자가 구체 예시나 차이를 그림으로 설명해 달라고 할 때.
- `research`: 원문을 더 확인해야 할 때만. 이번에 확인한 원문과 기존 조사 파일부터 읽고 전체 조사를 반복하지 않는다.

사용할 스킬은 Skill 도구가 있으면 호출하고, 없으면 세션 카탈로그의 SKILL.md를 읽는다. `code-review`는 고정점 이후 코드 diff 검수용이므로 이번 목적 적합성 문서 검수에 자동 적용하지 않는다.
